# DATABASE_DESIGN.md --- RZAdb

## 1. Назначение

RZAdb --- внутренняя система учёта оборудования РЗА, подстанций,
присоединений, устройств РЗА и связанной технической документации.

Этот документ фиксирует согласованные доменные и архитектурные решения
по базе данных.

Главное правило:

> Не добавлять новые сущности, поля, связи, ограничения или
> бизнес-правила без отдельного доменного решения.

## 13. Программы

Программа относится непосредственно к URZA. Программа также может быть
результатом задания типа `PROGRAM` через явную связь `task_id`.

Типы:

``` text
COMMISSIONING
DECOMMISSIONING
WORK
```

Запись программы содержит:

``` text
program_type
program_number
status
scan_file
editable_file
 task
creator
```

Скан программы обязателен. Редактируемый файл необязателен. Файлы
хранятся через object storage, а в БД хранятся метаданные и явные ссылки
на `files.id`.

### Согласованный MVP программ

-   MVP включает создание программы, прикрепление файлов, список,
    редактирование черновика и согласование.
-   Редактировать можно только черновик.
-   Редактируемый файл при редактировании можно оставить без изменений,
    заменить или убрать.
-   Утверждённую программу нельзя изменять; при необходимости изменения
    создаётся отдельная запись.
-   Версионирование программ не вводится.
-   Дополнительное уникальное ограничение на `program_number` не
    вводится без отдельного доменного решения.
-   Для номера действует базовая валидация; не вводить неподтверждённые
    правила формата или уникальности.
-   Архивирование программ не входит в текущий MVP и откладывается. При
    реализации архивирования использовать soft delete/archive, без
    физического удаления.
-   Связь программы с задачей должна быть согласованной: завершение
    задания типа `PROGRAM` требует существующего результата программы.
-   При отображении результата в карточке задания не показывать
    архивированную/удалённую запись.

### Транзакции и проверки

Создание/обновление программы и связанные изменения задачи должны быть
атомарны там, где они составляют одну бизнес-операцию. Проверять права
доступа к доменному объекту и каждому файлу через общий file-access
contract; не создавать обходные публичные file routes.

### Текущее состояние вкладки «Программы» (13.10.2026)

Ниже фиксируется подтверждённое состояние по выполненным этапам. Это не
требование создавать новые модели или менять существующий workflow.

**Реализовано:**

1.  Создание программы в контексте URZA, обязательный скан,
    необязательный редактируемый файл, список и действия согласования.
2.  Создание программы из задания типа `PROGRAM` с сохранением
    `task_id`. Создание результата не закрывает задание автоматически.
3.  Начальный статус зависит от роли: `MANAGER` --- «Утверждена»;
    `ENGINEER`, `ADMIN` и `SUPERADMIN` --- «Черновик».
4.  Редактирование только черновика. Редактируемый файл можно оставить,
    заменить или убрать; утверждённую программу нельзя изменять.
5.  Результат программы показывается в карточке связанного задания
    только при наличии действующей записи; при отсутствии или
    архивировании/удалении результата блок не отображается.
6.  Самостоятельные программы автора включены в общий список «Задания»
    через существующий `WorkItem`-сервис. Это реализовано и не должно
    возвращаться в TODO.
7.  Ссылка на самостоятельную программу из общего списка ведёт на
    `/objects/urza/{id}?tab=programs`, сохраняя контекст дерева объектов
    и открывая вкладку «Программы».
8.  В таблице общего списка «Задания» отображаются ссылка «Открыть» и
    статус. Действия `WorkItem` не обязаны дублироваться в таблице:
    кнопка «Отправить на согласование» находится в карточке задания.
    Тест должен соответствовать этому UI-контракту.

**Ограничения текущего MVP:**

-   Не вводить версионирование программ.
-   Не редактировать утверждённую запись; для изменения создавать
    отдельную запись.
-   Не добавлять дополнительную уникальность `program_number` без
    отдельного доменного решения.
-   Не вводить более строгую валидацию номера без согласования.
-   Архивирование программ отложено; в будущем использовать soft
    delete/archive, без физического удаления.
-   Не закрывать `Task` только из-за создания программы.
-   Не дублировать результат программы, связанный с `Task`, как
    самостоятельный элемент в одной и той же рабочей очереди.

**Проверки и точность статуса:**

-   На отдельных этапах проходили целевые тесты создания, редактирования
    черновика, файловых операций и списка; ранее сообщалось о 799
    зелёных тестах на более раннем этапе.
-   13.10.2026 после изменения списка «Задания» адресные тесты прошли;
    после обновления устаревшего ожидания в
    `tests/presentation/routes/test_tasks.py` сообщено о 89 прошедших
    адресных тестах, успешных Ruff для production-файлов и
    `git diff --check`.
-   Полный `pytest` после последних изменений не запускался. Не
    объявлять полный набор тестов зелёным без нового результата запуска.

**Решения от 13.10.2026:**

-   Самостоятельные программы уже входят в общий список «Задания»; это
    завершённая функциональность.
-   Список оставляет действия на карточке задания, а не дублирует все
    кнопки в таблице.
-   UX/UI страницы «Задания» сначала проектировать отдельно; до
    согласования не менять workflow и не перестраивать таблицу
    произвольно.
-   Codex CLI оставлять для глобальных и сложных задач. Точечный анализ
    и небольшие исправления выполнять в рабочем диалоге, когда это
    возможно.

Для URZA существует одна группа инструкции:


``` text

effective_date
change_description
change_justification
scan_file
editable_file
creator
```

Скан инструкции обязателен.

Редактируемый файл необязателен.

Исторические версии не удаляются.

Создание новой версии:

``` text
current version
      ↓

      ↓

```

При первом открытии истории она свернута.

Типы задач:

``` text
OTD
SETTINGS
SCHEMES
MAINTENANCE
PROGRAM
```

Статусы:

``` text
CREATED
ASSIGNED
IN_PROGRESS
COMPLETED
UNDER_REVIEW

```

Активные рабочие состояния:

``` text
ASSIGNED
IN_PROGRESS
UNDER_REVIEW
```

Инспекции/осмотры ПС --- отдельный процесс и не должны автоматически
становиться обычными Tasks.

### Доступ к заданиям и переназначение

-   `AccessService.can_access_urza()` проверяет область доступа
    пользователя к URZA.
-   Инженер (`ENGINEER`) видит в списке только задания, назначенные ему
    (`task.assigned_to == current_user.id`).
-   При прямом открытии задания проверяются и доступ к URZA, и
    назначение текущему инженеру. Для инженера, которому задание больше
    не назначено, доступ запрещается (403).
-   Менеджер сохраняет доступ к заданиям в пределах своей области
    доступа.
-   Переназначение меняет исполнителя и связанные с назначением данные,
    но сохраняет основной `deadline_at` задания.
-   В карточке должен отображаться текущий исполнитель.
-   Результат задания типа `PROGRAM` показывается только при наличии
    действующего результата; карточка без результата не должна
    показывать пустой блок результата.
-   Эти правила должны быть покрыты регрессионными тестами для списка,
    прямого URL, менеджера, смены исполнителя, основного срока и
    отображения результата.

### Рабочий процесс

Поддерживаемый workflow включает назначение, принятие/отказ, выполнение,
передачу на согласование, согласование, возврат на доработку и закрытие.
Конкретные допустимые переходы определяются существующим `TaskService`;
не добавлять новые переходы без доменного решения.

## 19. Files

Бинарные данные не хранить в PostgreSQL.

Целевая архитектура:

``` text
Domain entity
    ↓
File metadata
    ↓
ObjectStorage
```

Целевой storage:

``` text
S3-compatible object storage
```

Локальное хранилище используется в development.

Не использовать универсальную полиморфную модель:

``` text
File(owner_type, owner_id)
```

Использовать явные FK:

``` text
scan_file_id
editable_file_id
signed_form_file_id
...
```

### Общий механизм доступа

``` text
User
 ↓
AccessService
 ↓
domain object access
 ↓
FileAccessService
 ↓
File
 ↓
ObjectStorage
 ↓
Просмотр / Скачать
```

### Принятые решения

-   `AccessService` --- источник истины для доступа к доменным объектам.
-   `FileOwnerResolver` определяет владельца `File` через явные FK.
-   Один `File` имеет одного однозначного владельца; несколько file
    roles у одного владельца допустимы.
-   Разные владельцы одного `File` считаются неоднозначным техническим
    состоянием; доступ запрещается.
-   Orphan-файлы без владельца остаются техническим состоянием и не
    доступны обычному пользователю.
-   Архивирование владельца не блокирует чтение его файлов, если
    пользователь может просматривать архивный объект.
-   Архивированный `File` сам по себе недоступен через обычные read
    routes.
-   Для `Inspection` владелец файла определяется через
    `Inspection.substation_id`.
-   Для уже созданного результата осмотра авторизация не зависит от
    `InspectionTask`.
-   Просмотр и скачивание используют общий защищённый механизм; PDF
    viewer не требуется.

### Текущее состояние

Уже реализованы и проверены:

-   `FileOwnerResolver`;
-   `FileAccessService`;
-   защищённые `/view` и `/download` routes;
-   authentication / owner / archive / orphan / ambiguous ownership
    checks.

Следующий этап Files --- write/UI: upload, привязка файлов и полноценные
file actions в документных вкладках URZA.

## 21. Audit contract

Универсальный audit-refactor завершён.

Стандартный набор:

``` text
created_at
created_by
updated_at
updated_by
deleted_at
deleted_by
```

Смысл:

``` text
created_at  — когда создано
created_by  — кто создал

updated_at  — когда последний раз изменено
updated_by  — кто последний изменил

deleted_at  — когда архивировано
 deleted_by  — кто архивировал
```

Audit-поля должны быть реализованы централизованно через базовые mixins.

Audit не должен зависеть от UI.

## 22. Транзакции

Одна бизнес-операция должна быть атомарной.

Пример создания новой версии:

``` text
BEGIN

create new version
update required metadata
preserve old version

COMMIT
```

Не оставлять частично выполненную бизнес-операцию.

Repository не выполняет `commit()` без архитектурной причины.

## 24. Индексы и ограничения

Индексы создаются исходя из реальных запросов.

Основные кандидаты:

-   foreign keys;
-   `deleted_at` в active queries;

## 32. Статусы самостоятельных документов и согласование

**Решение зафиксировано: 13.10.2026.**

### 32.1. Общий принцип

Самостоятельные документы, изменяемые инженером без предварительного
`Task`, должны иметь собственный жизненный цикл согласования. Для этого
используется существующий `DocumentStatus`, если фактическая модель и
тип поля позволяют его переиспользовать. Не создавать отдельные
перечисления без технической необходимости.

Базовый цикл:

``` text
DRAFT → UNDER_REVIEW → APPROVED
             │
             └── возврат на исправление → DRAFT
```

Согласование документа и workflow `Task` --- разные процессы:

-   `Task.status` управляет назначением, исполнением, рассмотрением
    результата задания и закрытием;
-   `DocumentStatus` управляет состоянием самостоятельного документа или
    его версии;
-   связанный с `Task` документ не должен дублироваться как
    самостоятельная работа в одной и той же рабочей очереди.

### 32.2. Где хранить статус

Статус размещается на сущности, которая фактически проходит
согласование:

-   `TORecord` --- статус записи технического обслуживания;
-   `OTDVersion` --- статус конкретной версии ОТД, не логической группы
    `OTD`;
-   `RZAInstructionVersion` --- статус версии инструкции РЗА подстанции;
-   `SelectivitySchemeVersion` --- статус версии схемы селективности
    подстанции.

Перед изменением проверить фактические типы моделей и существующий
`DocumentStatus`. Не дублировать статус на родительской сущности и
версии одновременно без отдельного обоснования.

Для версионируемых документов утверждение относится к конкретной версии.
Исторические версии сохраняются. Утверждение новой версии не должно
незаметно уничтожать или переписывать историю предыдущей версии.

### 32.3. Миграция существующих данных

Изменения схемы выполнять через Alembic. Миграция должна:

-   добавлять нужные колонки с корректными типами и ограничениями;
-   назначать существующим записям обоснованные начальные статусы;
-   учитывать актуальные и исторические версии;
-   не помечать все существующие записи автоматически как `DRAFT` или
    `APPROVED` без проверки семантики данных;
-   иметь корректный downgrade, насколько это возможно без потери уже
    записанных статусов.

До реализации определить правила backfill по существующим данным. Не
добавлять универсальный статус завершённости, если он не нужен
конкретной модели.

### 32.4. Раздел «На проверке»

Самостоятельные записи `TORecord`, версии ОТД, версии инструкции РЗА
подстанции и версии схемы селективности должны попадать в «На проверке»,
когда они ожидают решения и текущий пользователь имеет полномочия
принять это решение.

Результаты, связанные с `Task`, продолжают проходить существующий
workflow задания и не должны дублироваться в очереди самостоятельных
документов.

Действия approve/return должны выполняться через application/service
слой с проверками роли, доступа к объекту и зоны ответственности. UI не
является механизмом авторизации.

### 32.5. Осмотры и основные сведения подстанции

`Inspection` / «Осмотры» сохраняет отдельный workflow. Не переводить
осмотры на общий `DocumentStatus` и не включать их автоматически в
обычные задания или очередь самостоятельных документов.

Основные сведения подстанции редактируются напрямую уполномоченными
ролями `ADMIN`, `MANAGER`, `SUPERADMIN` в рамках их прав доступа. Для
этих изменений не вводить workflow согласования и статусы `UNDER_REVIEW`
/ `APPROVED`.

### 32.6. Реализация

Изменения выполнять небольшими этапами:

1.  Обновить модели и enum/status contract.
2.  Создать Alembic-миграцию и backfill существующих данных.
3.  Добавить/дополнить сервисные переходы и проверки доступа.
4.  Подключить самостоятельные документы к рабочей зоне.
5.  Сохранить отдельный workflow `Task` и `Inspection`.

## 33. Редактирование основных сведений URZA --- решение и реализация 18.10.2026

### 33.1. Область функциональности

Основные сведения существующего устройства URZA можно редактировать с
карточки устройства. Используется существующая сущность URZA и
существующий DTO `URZACreate` как входная схема обновления. Новая
сущность, поле или отдельный статус жизненного цикла для редактирования
не вводятся.

Редактируемые поля соответствуют текущей схеме формы:

-   `dispatch_name`;
-   `rdu_subordination`;
-   `inventory_number`;
-   `commissioning_date`;
-   `status`;
-   `element_base`;
-   `category`;
-   `room_category`;
-   `complexity`.

Связь устройства с присоединением не меняется через эту форму.

### 33.2. Роли и авторизация

Редактировать основные сведения URZA могут:

-   `SUPERADMIN` --- в пределах предусмотренного глобального доступа;
-   `ADMIN`;
-   `MANAGER`.

`ENGINEER` и `SPECIALIST` не могут редактировать основные сведения URZA.

Скрытие кнопки «Изменить» в шаблоне --- только UX-ограничение. GET и
POST маршруты обязаны независимо проверять роль и доступ к конкретному
URZA через существующий `ObjectService`/механизм авторизации. Нельзя
считать UUID объекта или скрытую кнопку доказательством доступа.

### 33.3. Application и repository

-   Изменение выполняется через
    `URZAService.update(urza_id, actor_id, data)`.
-   `updated_by` обновляется значением `actor_id`.
-   `dispatch_name` должен быть уникальным внутри того же присоединения
    согласно действующему правилу URZA.
-   При проверке дубликата текущая запись исключается по `exclude_id`,
    чтобы сохранение собственного имени не считалось конфликтом.
-   Repository выполняет обновление и `flush`, но не `commit`;
    управление транзакцией остаётся централизованным.
-   Конфликт имени представлен `URZANameConflictError`.

Не переносить бизнес-валидацию в Jinja2 или исключительно в routes.
Проверка доступа должна выполняться сервером, а бизнес-правила ---
application/domain слоем.

### 33.4. HTTP/UI-контракт

-   Маршруты редактирования находятся в
    `app/presentation/routes/urza_objects.py` и подключены в приложении.
-   Форма `objects/urza_form.html` переиспользуется для создания и
    редактирования; режим определяется параметром `is_edit`.
-   Успешный HTMX POST возвращает `204` и `HX-Redirect` на
    `/objects/urza/{urza_id}`.
-   Ошибка валидации входных значений и конфликт имени возвращают форму
    с HTTP `422`, сообщением об ошибке и введёнными значениями.
-   Существующий сценарий создания URZA с карточки присоединения
    сохраняется без дублирования бизнес-логики.
