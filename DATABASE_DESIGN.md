# DATABASE_DESIGN.md — RZAdb

## 1. Назначение

RZAdb — внутренняя система учёта оборудования РЗА, подстанций, присоединений, устройств РЗА и связанной технической документации.

Этот документ фиксирует согласованные доменные и архитектурные решения по базе данных.

Главное правило:

> Не добавлять новые сущности, поля, связи, ограничения или бизнес-правила без отдельного доменного решения.

## 9. ОТД

ОТД имеет текущую версию и исторические версии.

```text
OTD
├── current version
└── historical versions
```

Старые версии не удаляются.

### Назначение ОТД

```text
RZA
SA
PA
RA
```

Для ОТД подпись не обязательна.

### Versioning

Создание новой версии:

```text
current version
      ↓
new version
      ↓
old version remains in history
```

Одна бизнес-операция создания новой версии должна быть атомарной.

В UI исторические версии доступны через HTMX.

## 13. Программы

Программа относится непосредственно к URZA. Программа также может быть результатом задания типа `PROGRAM` через явную связь `task_id`.

Типы:

```text
COMMISSIONING
DECOMMISSIONING
WORK
```

Запись программы содержит:

```text
program_type
program_number
status
scan_file
editable_file
 task
creator
```

Скан программы обязателен. Редактируемый файл необязателен.
Файлы хранятся через object storage, а в БД хранятся метаданные и явные ссылки на `files.id`.

### Согласованный MVP программ

- MVP включает создание программы, прикрепление файлов, список, редактирование черновика и согласование.
- Редактировать можно только черновик.
- Редактируемый файл при редактировании можно оставить без изменений, заменить или убрать.
- Утверждённую программу нельзя изменять; при необходимости изменения создаётся отдельная запись.
- Версионирование программ не вводится.
- Дополнительное уникальное ограничение на `program_number` не вводится без отдельного доменного решения.
- Для номера действует базовая валидация; не вводить неподтверждённые правила формата или уникальности.
- Архивирование программ не входит в текущий MVP и откладывается. При реализации архивирования использовать soft delete/archive, без физического удаления.
- Связь программы с задачей должна быть согласованной: завершение задания типа `PROGRAM` требует существующего результата программы.
- При отображении результата в карточке задания не показывать архивированную/удалённую запись.

### Транзакции и проверки

Создание/обновление программы и связанные изменения задачи должны быть атомарны там, где они составляют одну бизнес-операцию. Проверять права доступа к доменному объекту и каждому файлу через общий file-access contract; не создавать обходные публичные file routes.

## 14. Инструкция URZA

Инструкция URZA является отдельной сущностью уровня URZA.

```text
URZA
└── URZAInstruction
    └── URZAInstructionVersion[]
```

`URZAInstruction` — логическая группа.

`URZAInstructionVersion` — конкретная версия документа.

Для URZA существует одна группа инструкции:

```text
URZAInstruction.urza_id UNIQUE
```

### Версия инструкции

Содержит:

```text
version_number
effective_date
change_description
change_justification
scan_file
editable_file
creator
```

Скан инструкции обязателен.

Редактируемый файл необязателен.

Исторические версии не удаляются.

Создание новой версии:

```text
current version
      ↓
new version
      ↓
old version remains available
```

В UI история версий доступна через HTMX.

При первом открытии истории она свернута.

После выбора версии через историю она остаётся раскрытой.

## 17. Tasks

Типы задач:

```text
OTD
SETTINGS
SCHEMES
MAINTENANCE
PROGRAM
```

Статусы:

```text
CREATED
ASSIGNED
IN_PROGRESS
COMPLETED
UNDER_REVIEW
CLOSED
REJECTED
```

Активные рабочие состояния:

```text
ASSIGNED
IN_PROGRESS
UNDER_REVIEW
```

Инспекции/осмотры ПС — отдельный процесс и не должны автоматически становиться обычными Tasks.

### Доступ к заданиям и переназначение

- `AccessService.can_access_urza()` проверяет область доступа пользователя к URZA.
- Инженер (`ENGINEER`) видит в списке только задания, назначенные ему (`task.assigned_to == current_user.id`).
- При прямом открытии задания проверяются и доступ к URZA, и назначение текущему инженеру. Для инженера, которому задание больше не назначено, доступ запрещается (403).
- Менеджер сохраняет доступ к заданиям в пределах своей области доступа.
- Переназначение меняет исполнителя и связанные с назначением данные, но сохраняет основной `deadline_at` задания.
- В карточке должен отображаться текущий исполнитель.
- Результат задания типа `PROGRAM` показывается только при наличии действующего результата; карточка без результата не должна показывать пустой блок результата.
- Эти правила должны быть покрыты регрессионными тестами для списка, прямого URL, менеджера, смены исполнителя, основного срока и отображения результата.

### Рабочий процесс

Поддерживаемый workflow включает назначение, принятие/отказ, выполнение, передачу на согласование, согласование, возврат на доработку и закрытие. Конкретные допустимые переходы определяются существующим `TaskService`; не добавлять новые переходы без доменного решения.

## 19. Files

Бинарные данные не хранить в PostgreSQL.

Целевая архитектура:

```text
Domain entity
    ↓
File metadata
    ↓
ObjectStorage
```

Целевой storage:

```text
S3-compatible object storage
```

Локальное хранилище используется в development.

Не использовать универсальную полиморфную модель:

```text
File(owner_type, owner_id)
```

Использовать явные FK:

```text
scan_file_id
editable_file_id
signed_form_file_id
...
```

### Общий механизм доступа

```text
User
 ↓
AccessService
 ↓
domain object access
 ↓
FileAccessService
 ↓
File
 ↓
ObjectStorage
 ↓
Просмотр / Скачать
```

### Принятые решения

- `AccessService` — источник истины для доступа к доменным объектам.
- `FileOwnerResolver` определяет владельца `File` через явные FK.
- Один `File` имеет одного однозначного владельца; несколько file roles у одного владельца допустимы.
- Разные владельцы одного `File` считаются неоднозначным техническим состоянием; доступ запрещается.
- Orphan-файлы без владельца остаются техническим состоянием и не доступны обычному пользователю.
- Архивирование владельца не блокирует чтение его файлов, если пользователь может просматривать архивный объект.
- Архивированный `File` сам по себе недоступен через обычные read routes.
- Для `Inspection` владелец файла определяется через `Inspection.substation_id`.
- Для уже созданного результата осмотра авторизация не зависит от `InspectionTask`.
- Просмотр и скачивание используют общий защищённый механизм; PDF viewer не требуется.

### Текущее состояние

Уже реализованы и проверены:

- `FileOwnerResolver`;
- `FileAccessService`;
- защищённые `/view` и `/download` routes;
- authentication / owner / archive / orphan / ambiguous ownership checks.

Следующий этап Files — write/UI: upload, привязка файлов и полноценные file actions в документных вкладках URZA.

## 21. Audit contract

Универсальный audit-refactor завершён.

Стандартный набор:

```text
created_at
created_by
updated_at
updated_by
deleted_at
deleted_by
```

Смысл:

```text
created_at  — когда создано
created_by  — кто создал

updated_at  — когда последний раз изменено
updated_by  — кто последний изменил

deleted_at  — когда архивировано
 deleted_by  — кто архивировал
```

Audit-поля должны быть реализованы централизованно через базовые mixins.

Audit не должен зависеть от UI.

## 22. Транзакции

Одна бизнес-операция должна быть атомарной.

Пример создания новой версии:

```text
BEGIN

create new version
update required metadata
preserve old version

COMMIT
```

Не оставлять частично выполненную бизнес-операцию.

Repository не выполняет `commit()` без архитектурной причины.

## 24. Индексы и ограничения

Индексы создаются исходя из реальных запросов.

Основные кандидаты:

- foreign keys;
- `deleted_at` в active queries;
- поля поиска;
- поля уникальности;
- часто используемые фильтры.

Не добавлять индексы «на всякий случай».

SAP/ASUREO не делать глобально уникальными без отдельного доменного решения.

### Последняя подтверждённая работа с заданиями (11.10.2026)

Пользователь вручную подтвердил:

- переназначенное задание исчезает из списка прежнего исполнителя и появляется у нового;
- менеджер продолжает видеть задания в своей области доступа;
- карточка показывает актуального исполнителя;
- основной срок задания не изменяется при переназначении;
- результат программы отображается в карточке задания, если он существует, и отсутствует, если результата нет;
- прежний исполнитель не может открыть переназначенное задание по прямому URL;
- новый исполнитель и менеджер с необходимыми правами открывают задание.

Следующий шаг — закрепить поведение регрессионными тестами и выполнить актуальный запуск тестов. Результат последнего полного запуска после этих изменений ещё не подтверждён.

Косметический UI-аудит не должен вытеснять основной функционал. Безопасность, целостность данных и корректность workflow важнее косметических улучшений.

## 28. Отложенные вопросы

### Исторические ТО

Не изменять `historical_data` без отдельного решения.

Исходный workflow требует отдельного процесса ввода исторических данных.

### Уникальность dispatch_name

Перед добавлением DB-ограничений необходимо отдельно зафиксировать области уникальности `dispatch_name` для Enterprise / Substation / Connection / URZA и проверить существующие данные.

### S3

Production S3 подключать после стабилизации file abstraction и завершения базовой write/UI работы с файлами.

### Backup / cold storage

Проектировать после стабилизации storage contract.

## 29. Передача контекста между сессиями

При продолжении разработки:

1. Сначала проверить фактический `git status` и код; документ описывает согласованные решения, но не заменяет проверку текущего состояния рабочей копии.
2. Начать с регрессионных тестов последней работы с заданиями.
3. Затем завершить редактирование черновика программы в рамках MVP, не вводя версии, дополнительную уникальность номера или архивирование на этом этапе.
4. Делать небольшие изменения, запускать относящиеся тесты, фиксировать реально выполненные команды и результаты.
5. Обновлять этот документ только при подтверждённом изменении решения или статуса.

## 30. Основной принцип

База данных должна отражать согласованную предметную область.

Не:

- добавлять поля «на всякий случай»;
- создавать дублирующие сущности;
- менять БД ради косметического UI;
- физически удалять исторические версии;
- смешивать domain rules и infrastructure details.

При неоднозначности:

```text
исследование
→ вопрос пользователю
→ доменное решение
→ реализация
```

## 31. Рабочая зона: задания и самостоятельные документы

**Дата фиксации решения: 12.10.2026**

### 31.1. Два контура работы

В UI разделяются два способа организации работы.

**Задания руководителя (`Task`)**

- Работа инициируется руководителем и проходит существующий workflow `Task`.
- Назначение, исполнитель, сроки, статусы, согласование результата, возврат на доработку, закрытие и история остаются в рамках текущей модели и `TaskService`.
- Новый UI не должен менять бизнес-процесс заданий.

**Самостоятельные документы («Мои документы»)**

- Инженер самостоятельно создаёт или изменяет документ без предварительного задания руководителя.
- Документ проходит собственный жизненный цикл и может требовать согласования/утверждения.
- Используются существующие модели, сервисы, статусы, версии и правила действий конкретного типа документа.
- Не создавать отдельную универсальную сущность «Прямая задача» и не имитировать `Task` для отображения документа.

### 31.2. Структура рабочей зоны

Согласована следующая концепция вкладок:

```text
Рабочая зона
├── Задания
│   ├── Активные
│   └── Завершённые
├── Мои документы
│   ├── Активные
│   └── Завершённые
└── На проверке
    └── элементы, по которым руководителю требуется принять решение
```

«На проверке» — рабочее представление для руководителя, ограниченное его областью доступа. Это не новая доменная сущность и не новый workflow.

### 31.3. Счётчики

- На вкладках показываются счётчики активных элементов.
- Счётчики рассчитываются на сервере и учитывают роль пользователя, назначение, область доступа и фактическое право выполнить требуемое действие.
- Счётчик «На проверке» включает только доступные руководителю элементы, ожидающие его решения.
- Внутренние счётчики «Активные» и «Завершённые» должны соответствовать правилам соответствующего контура.
- Не допускать двойного учёта одного результата в одном списке, если документ связан с `Task`.
- Просрочка может отображаться отдельным индикатором и не должна незаметно менять смысл общего счётчика.

### 31.4. Статусы и завершённость

Не вводить универсальный статус `COMPLETED` для разных типов документов.

- Для `Task` завершённость определяется правилами текущего workflow (в частности, `CLOSED` — закрытое задание).
- Для программ, уставок, схем и других документов завершённость определяется их собственными статусами и правилами сервиса.
- Нельзя считать документ или его логическую группу окончательно завершённой только по наличию утверждённой версии, если модель допускает дальнейшее создание версий/записей.
- Категории UI «Активные» и «Завершённые» не являются значениями БД и должны вычисляться на основе явных правил соответствующего типа сущности.
- Состав состояний для каждого типа нужно подтвердить по фактической модели/сервису до реализации. Не использовать автоматически все состояния, кроме одного, как эвристику завершённости.

### 31.5. Связанные и самостоятельные документы

- Документ, созданный в рамках `Task`, остаётся результатом задания и следует правилам соответствующего workflow.
- Самостоятельный документ без задания может отображаться в «Моих документах» по правилам своего типа.
- Не показывать один результат как две независимые работы только из-за того, что он связан с заданием.
- История `Task` и история версий/согласования документа — разные виды истории и не заменяют друг друга.
- `Inspection`/«Осмотры» остаётся отдельным процессом и не включается автоматически в `Task` или «Мои документы».

### 31.6. Первый этап реализации

Первый этап — UI без изменения схемы БД:

1. Проверить фактическую реализацию, текущую ветку и тесты.
2. Сохранить текущий workflow и список заданий.
3. Создать представление «Мои документы», начиная с самостоятельных программ, для которых уже существует сценарий получения программ на проверке (`task_id IS NULL`, статус и доступ проверяются действующим сервисом).
4. После проверки модели и правил поэтапно подключать другие типы документов.
5. Реализовать для руководителя представление «На проверке».
6. Добавить тесты на доступ, роли, счётчики, отсутствие дублей и категории активных/завершённых.

Новые модели, поля, связи и миграции для одной лишь навигации/счётчиков не добавлять. Если позже обнаружится необходимость хранить самостоятельный процесс как отдельную бизнес-сущность, сначала согласовать отдельное доменное решение.
