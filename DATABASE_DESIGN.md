# DATABASE_DESIGN.md — База данных РЗА

## 1. Цель

Этот документ фиксирует согласованную доменную модель базы данных РЗА и решения, принятые в ходе проектирования.

Структура:

Холдинг
└── Филиал
    └── Производственное отделение (ПО)
        └── Подстанция
            └── Присоединение
                └── УРЗА

## 2. Общие правила модели

Для основных сущностей используются:

- `id UUID PK`
- `created_at`
- `created_by`
- `updated_at`
- `updated_by`
- `deleted_at`
- `deleted_by`

Объекты ПС, присоединение и УРЗА физически не удаляются при обычном архивировании. Они переводятся в архив через `deleted_at`.

Архивирование родительского объекта каскадно архивирует потомков.

Восстановление родителя должно возвращать ветку в состояние, существовавшее непосредственно до архивирования родителя. Поэтому нельзя просто обнулять `deleted_at` у всех потомков: необходимо сохранить информацию о состоянии объектов до каскадного архивирования.

## 3. Enterprise

Одна сущность `Enterprise` используется для трёх уровней:

- Холдинг
- Филиал
- Производственное отделение

Поля:

- `id`
- `type`
- `parent_id`
- `full_name`
- `short_name`
- `sap_code`

Правила:

- Холдинг может иметь Филиалы.
- Филиал может иметь Производственные отделения.
- Только Производственное отделение может содержать Подстанции.
- Все поля из исходной модели сохраняются.

## 4. User

Поля:

- `id`
- `full_name`
- `initials` — вычисляются из ФИО
- `role`
- `email`
- `password_hash`
- `enterprise_id`
- `access_category`
- `sap_code` nullable
- `active`
- `login`

Роли:

- Суперадмин
- Администратор
- Специалист
- Руководитель
- Инженер

Привязка:

- Специалист → Холдинг или Филиал.
- Администратор/Руководитель/Инженер → Производственное отделение.
- Суперадмин → без enterprise binding.

## 5. Подстанция

`Substation`

Поля:

- `id`
- `enterprise_id` → Production Department
- `highest_voltage`
- `dispatch_name`
- `sap_code` nullable
- `asureo_code` nullable
- `latitude` nullable
- `longitude` nullable
- `address` nullable

Допустимые классы высшего напряжения:

- 500 кВ
- 220 кВ
- 110 кВ
- 35 кВ
- 10 кВ
- 6 кВ
- 0.4 кВ

SAP/ASUREO могут отсутствовать. Для заполненных значений одинаковое значение не должно повторяться; точная область уникальности должна быть закреплена отдельным DB-решением, если она ещё не формализована.

## 6. Присоединение

`Connection`

Поля:

- `id`
- `substation_id` → Substation
- `dispatch_name`
- `sap_code` nullable
- `asureo_code` nullable
- `rdu_subordination`
- `operational_current_type`

`operational_current_type`:

- постоянный
- выпрямленный
- переменный

Правила:

- обязательны все поля, кроме явно nullable SAP/ASUREO;
- диспетчерское имя присоединения уникально внутри одного Производственного отделения;
- одно присоединение может иметь любое количество УРЗА.

## 7. УРЗА

`URZA`

Поля:

- `id`
- `connection_id`
- `dispatch_name`
- `rdu_subordination`
- `inventory_number` nullable
- `commissioning_date`
- `status`
- `element_base`
- `category`
- `room_category`
- `complexity`
- вычисляемый `title`
- вычисляемый `maintenance_period`

Статусы:

- В работе
- В ремонте
- Выведено
- Резерв

Element base:

- Электромеханическая
- Микроэлектронная
- Микропроцессорная

Категория:

- I
- II
- III
- IV

Категория помещения:

- I
- II
- III

Правила:

- `inventory_number` nullable;
- остальные бизнес-поля обязательны;
- диспетчерское имя УРЗА уникально внутри одного Присоединения;
- одна УРЗА может иметь любое количество записей в доменах формуляров;
- УРЗА может быть RDU-подчинённой независимо от присоединения;
- complexity не влияет на период ТО;
- для сложной УРЗА обязательны все три типа программ: Ввод в работу, Вывод из работы, Производство работ.

### Title

Титул вычисляется из:

Холдинг + Филиал + Производственное отделение + ПС + Присоединение + УРЗА.

Не должен быть обычным редактируемым полем.

### Период ТО

Период рассчитывается по сочетанию:

- категории помещения;
- элементной базы.

Сложность УРЗА на период не влияет.

Используется таблица `MaintenancePeriodRule`, а не hard-coded if/else:

- `id`
- `room_category`
- `element_base`
- `maintenance_period_years`

Период — количество лет между профилактическими восстановлениями «В».

После 25 лет эксплуатации требуется визуально показать состояние, при котором необходимо принять решение о продлении срока службы или замене УРЗА.

## 8. ОТД

Один логический ОТД на одну УРЗА.

Система версионирования:

`OTD` → `OTDVersion`

`OTD`:

- `id`
- `urza_id` UNIQUE

Каждая версия — полный снимок текущих ОТД.

`OTDVersion` содержит:

- `id`
- `otd_id`
- `version_number`
- `effective_date`
- `created_at`
- `created_by`
- panel/cabinet type nullable
- panel/cabinet serial nullable
- panel/cabinet manufacture year nullable
- terminal type nullable
- terminal serial nullable
- terminal manufacture year nullable
- URZA service life
- software version nullable
- CT ratio nullable
- VT ratio nullable
- URZA scheme designation nullable
- URZA purpose

Назначение:

- РЗ
- СА
- ПА
- РА

ОТД — текстовое представление полей вида `Название поля: Значение`.

Нет скана, редактируемого файла или физической подписи.

При существенном изменении технических данных создаётся новая полная версия; старая остаётся доступной в истории.

## 9. Уставки

Один логический `SettingsForm` на УРЗА.

`SettingsForm`:

- `id`
- `urza_id` UNIQUE

`SettingsRecord`:

- `id`
- `settings_form_id`
- `change_date`
- `parameter_name`
- `initial_setting`
- `new_setting`
- `change_reason`
- `created_by`
- `created_at`
- `signed_form_file_id`
- `task_id` nullable

Каждая запись содержит только изменённые параметры.

Требуется скан подписанного формуляра.

Отдельный протокол не формируется.

Текущий сводный вид уставок не является частью текущего приложения; предусмотрена кнопка «Посмотреть уставки» и возможность отдельного сервиса в будущем.

## 10. Схемы

Один логический `SchemaForm` на УРЗА.

`SchemaForm`:

- `id`
- `urza_id` UNIQUE

`SchemaRecord`:

- `id`
- `schema_form_id`
- `schema_number`
- `schema_name`
- `change_description`
- `change_justification`
- `upload_date`
- `created_by`
- `scan_file_id`
- `editable_file_id`
- `signed_form_file_id`
- `task_id` nullable

Текущий тип схемы — только Исполнительная. Архитектура может быть расширена в будущем.

Для записи обязательны:

- скан схемы;
- редактируемая схема;
- скан подписанного формуляра.

История сохраняется, старые записи и документы доступны для скачивания.

Отдельно существует домен селективности ПС: скан селективности, редактируемый файл и история. Детальная модель этого домена ещё не финализирована.

## 11. ТО

ТО — журнал фактически выполненных работ.

Один `TORecord` = одно фактическое мероприятие.

Поля исходной записи:

- `id`
- `urza_id`
- `historical_data`
- `maintenance_date`
- `maintenance_type`
- `detected_deviations`
- `measures_taken`
- `created_by`
- `scan_protocol`
- `editable_protocol`

Дополнительно по принятым решениям:

- `task_id` nullable;
- подписанный формуляр обязателен;
- для типов, где требуется протокол, протокол обязателен;
- для ТК, О, ОСМ протокол не требуется;
- даже для ТК, О, ОСМ подписанный формуляр обязателен;
- `detected_deviations` по умолчанию: «Не выявлено»;
- `measures_taken` по умолчанию: «Не требуется».

Типы ТО:

- В — профилактическое восстановление
- К — профилактический контроль
- К1 — первый профилактический контроль
- Н — наладка
- Т — тестовый контроль
- ТК — технический контроль
- О — опробование
- ОСМ — технический осмотр
- ВП — внеочередная проверка
- ПП — послеаварийная проверка

Если обязательный протокол отсутствует, ТО не считается валидным результатом.

Планирование ТО не входит в текущий сервис; `planned_maintenance_date` рассматривается как вычисляемый/выходной показатель.

## 12. Программы

`Program` — отдельная сущность, связанная с УРЗА.

Одна УРЗА может иметь любое количество программ одного типа.

Типы:

- Вывод из работы
- Ввод в работу
- Производство работ

Поля:

- `id`
- `urza_id`
- `program_type`
- `program_number`
- `scan_file_id`
- `editable_file_id` nullable
- `task_id` nullable
- общие audit/soft-delete поля

`program_number` — реальный номер из внешнего источника, не генерируется системой.

Скан обязателен, редактируемая копия необязательна.

Физическая подпись находится на самой программе; отдельный подписанный формуляр не нужен.

Программы могут быть физически удалены после необходимого подтверждения; суперадмин может удалить без подтверждения.

## 13. Файлы

Общая сущность:

`File`

Минимально:

- `id`
- `s3_key`
- display/original name
- extension
- size
- mime_type
- uploaded_at
- audit fields

Файлы физически хранятся в S3-compatible storage.

Доменные сущности содержат явные FK:

- `scan_file_id`
- `editable_file_id`
- `signed_form_file_id`
- и т. п.

Не использовать полиморфного `owner_type + owner_id`.

Для удаления файла необходимо удалить объект из S3 и корректно обработать FK/ссылки, чтобы не появились orphan records.

## 14. Задания

`Task` — задание на выполнение одного конкретного типа работы с конкретной УРЗА.

Одно задание не объединяет несколько типов работ.

Типы:

- ОТД
- Уставки
- Схемы
- ТО
- Программы

Поля:

- `id`
- `urza_id`
- `work_type`
- `maintenance_type` nullable
- `description` nullable
- `created_by`
- `assigned_to`
- `status`
- `created_at`
- `assigned_at`
- `acceptance_deadline_at`
- `deadline_at`
- `completed_at`
- `closed_at`
- audit/soft-delete поля

Для ТО `maintenance_type` обязателен. Для остальных типов NULL.

### Титул задания

Формируется автоматически:

`ПС, Присоединение, УРЗА: [содержание работы]`

Для ТО содержание включает объём/тип ТО, например:

`ПС ..., присоединение ..., УРЗА ...: провести ТО в объёме В`

Титул не вводится вручную.

Описание необязательно.

### Workflow

Согласованная логика:

`Создано`
→ `Назначено инженеру`
→ `В работе`
→ `Работа выполнена`
→ `Проверка руководителем`
→ `Подтверждено/Закрыто`

Из `Назначено инженеру`:

- принять → `В работе`;
- отклонить → `Отклонено`.

При отклонении причина обязательна.

Руководитель получает уведомление и может назначить задание заново.

При `Работа выполнена`:

- руководитель проверяет;
- подтвердить → `Закрыто`;
- отправить на доработку → причина обязательна → задание сразу возвращается в `В работе`.

`Просрочено` — рабочий статус/состояние, которое не создаёт отдельного контроля. Просроченное задание после выполнения проходит обычную проверку.

### Сроки

- выполнение: 7 дней от создания;
- принятие: 1 день от назначения;
- продление не предусмотрено;
- при переназначении deadline не пересчитывается.

Если срок принятия истёк:

- статус остаётся «Назначено инженеру»;
- руководителю отправляется уведомление;
- инженер всё ещё может принять/отклонить.

Переназначение возможно только в статусе «Назначено инженеру».

## 15. TaskHistory

`TaskHistory` хранит неизменяемую историю workflow.

Поля:

- `id`
- `task_id`
- `event_type`
- `old_status`
- `new_status`
- `actor_id`
- `comment`
- `created_at`

История должна отражать:

- создание;
- назначение;
- переназначение;
- принятие;
- отклонение + причину;
- начало работы;
- просрочку;
- выполнение;
- отправку на доработку + причину;
- возврат в работу;
- подтверждение;
- закрытие;
- удаление ошибочно созданного задания.

Одно и то же задание сохраняется как один `Task` при повторном назначении.

## 16. Связь Task с результатом

Записи формуляров имеют nullable `task_id`.

Если запись создана из задания, связь устанавливается автоматически.

Если запись создаётся вне задания:

`task_id = NULL`.

Руководитель не должен подтверждать задание, пока система не проверит обязательный результат.

Перед `Работа выполнена` система проверяет комплектность результата в зависимости от `work_type` и, для ТО, `maintenance_type`.

## 17. Уведомления

`Notification`

Минимальная модель:

- `id`
- `user_id`
- `type`
- `title`
- `message`
- `task_id` nullable
- `created_at`
- `read_at` nullable

`read_at = NULL` → непрочитано.

Непрочитанные уведомления выделяются в колокольчике.

После просмотра уведомление считается закрытым и исчезает из основного списка, но запись в БД сохраняется.

Email-настройки пользователя не отключают обязательные служебные уведомления.

### Email

- поступление задания;
- напоминания за 3, 2 и 1 день до deadline;
- уведомление о просрочке;
- уведомление руководителю о непринятом задании за 1 день.

После закрытия задания дальнейшие напоминания прекращаются.

## 18. Представления заданий

### Инженер — «Мои задания»

Показываются:

- статус;
- ПС;
- присоединение;
- УРЗА;
- тип работы;
- вид ТО, если применимо;
- дедлайн;
- описание, если есть;
- действие;
- ссылка на карточку УРЗА.

### Руководитель — «На проверке»

Показываются:

- ПС;
- присоединение;
- УРЗА;
- тип работы;
- вид ТО;
- ФИО инженера;
- ссылка на карточку УРЗА.

Из карточки УРЗА руководитель смотрит формуляры/документы и принимает решение.

### Руководитель — «Активные задания»

Все выданные и ещё не закрытые задания:

- Назначено инженеру
- В работе
- Просрочено
- Работа выполнена

Задание «Работа выполнена» одновременно может отображаться в «Активных заданиях» и «На проверке».

### Руководитель — «История заданий»

Закрытые задания с результатами, документами и полной историей workflow.

## 19. Удаление

Для ошибочно созданного Task:

- до начала работы допускается удаление;
- после перехода в «В работе» физическое удаление задания запрещено;
- закрытые задания сохраняются;
- удаление до начала работы фиксируется в истории.

Права удаления Task:

- Руководитель — ошибочно созданное задание до начала работы;
- Суперадмин — без ограничения;
- Инженер — не удаляет задания;
- Администратор и Специалист — не управляют удалением Task.

Для других ниже-УРЗА объектов действует отдельное правило подтверждаемого удаления:

- инженер/администратор могут инициировать;
- руководитель может инициировать и подтвердить своё удаление;
- суперадмин может удалить напрямую.

## 20. Что ещё не финализировано

Не считать окончательными без отдельного решения:

- точную область уникальности SAP/ASUREO;
- детальную модель селективности ПС;
- окончательный механизм восстановления точного состояния после каскадного архивирования;
- точную реализацию автоматической проверки комплектности каждого типа задания;
- отдельные правила удаления исторических записей формуляров;
- расширение типов программ/схем в будущем;
- второй этап со статистической рассылкой.
