# AGENTS.md — RZAdb / База Данных РЗА

## 1. Назначение

RZAdb — внутреннее веб-приложение для учёта оборудования РЗА, подстанций, присоединений, устройств РЗА, технической документации, формуляров, уставок, схем, ТО, программ, инструкций, осмотров и задач.

Проект некоммерческий.

Этот файл — рабочие инструкции для coding agents. `DATABASE_DESIGN.md` фиксирует согласованные доменные и архитектурные решения.

Главное правило: **не добавлять новые сущности, поля, связи или бизнес-правила без отдельного доменного решения пользователя.**

## 8. Доменные правила

- Напряжения: `500, 220, 110, 35, 10, 6, 0.4`.
- SAP/ASUREO не делать глобально уникальными без отдельного доменного решения.
- Диспетчерские имена уникальны в соответствующих доменных областях.
- Имя УРЗА уникально внутри присоединения.
- УРЗА II обслуживается персоналом категорий II, III, IV.
- ОТД, Уставки, Схемы, ТО и Программы — один логический уровень под URZA.
- Инструкция URZA — отдельная версионируемая сущность под URZA.
- Инструкция РЗА — отдельная сущность уровня Substation.
- Формуляр — логическая группировка.
- Старые версии документов не удаляются.
- Для ТО подписанная форма/скан обязательна.
- Для ОТД подпись не обязательна.
- Плановая дата ТО хранится для последующего микросервиса.
- Inspection/Осмотр ПС — отдельный процесс, не обычная Task.

## 10. Files

Бинарные файлы не хранить в PostgreSQL.

Целевой storage: S3-compatible object storage.

Не использовать универсальную полиморфную связь:

```text
File(owner_type, owner_id)
```

Использовать явные FK от доменных сущностей к `files.id`.

Целевой общий механизм:

```text
пользователь
→ AccessService
→ доменный объект
→ FileAccessService
→ File
→ ObjectStorage
→ Просмотр / Скачать
```

### Принятые решения по file access

- `AccessService` остаётся источником истины для прав на доменные объекты.
- `FileAccessService` определяет, имеет ли пользователь право читать конкретный `File` через его владельца.
- `FileOwnerResolver` определяет владельца по существующим явным FK; полиморфные `owner_type/owner_id` не вводятся.
- Один `File` должен иметь одного однозначного владельца. Несколько ролей файлов у одного владельца допустимы.
- Если у `File` несколько разных владельцев, состояние считается неоднозначным и доступ запрещается как техническая ошибка.
- Orphan-файл без владельца не доступен обычному пользователю; очистка orphan-файлов — отдельная будущая операция.
- Архивирование владельца не блокирует доступ к его файлам, если сам пользователь имеет право просматривать архивный объект.
- Архивированный сам `File` недоступен через обычные read routes.
- Для `Inspection` владелец файла определяется через `Inspection.substation_id`.
- Отдельная авторизация через `InspectionTask` для уже созданного результата осмотра не требуется.
- Просмотр и скачивание используют один общий защищённый механизм; PDF viewer не требуется.
- Не создавать отдельные несогласованные file routes для каждой сущности.

### Текущее состояние

Уже реализованы и проверены:

- `FileOwnerResolver`;
- `FileAccessService`;
- защищённые routes просмотра и скачивания;
- проверки аутентификации, владельца, архивного `File`, orphan и ambiguous ownership.

Следующая работа с файлами — **write/UI**: загрузка, привязка и действия с файлами в документных вкладках URZA.

### Программы: подтверждённое состояние и решения MVP (обновлено 13.10.2026)

#### Реализованные сценарии

- Программа принадлежит URZA; результат задания типа `PROGRAM` связывается с заданием через `task_id`.
- Реализованы создание программы, обязательный скан, необязательный редактируемый файл, список, согласование и синхронизация результата с заданием в рамках существующего workflow.
- Создание программы из задания сохраняет связь с исходным `Task`. Сам факт создания программы не завершает задание: завершение выполняется существующим workflow задания.
- Для карточки задания показывается результат программы (тип, номер, статус и файлы), если действующий результат существует; при отсутствии результата или при архивной/удалённой записи блок результата не показывается.
- Создание и связанные изменения, являющиеся одной бизнес-операцией, выполняются атомарно.
- Реализовано редактирование программы только в статусе «Черновик». Редактируемый файл можно оставить, заменить или убрать; тесты этого сценария проходили на соответствующем этапе.
- Начальный статус при создании зависит от роли: `MANAGER` — «Утверждена»; `ENGINEER`, `ADMIN` и `SUPERADMIN` — «Черновик». Это зафиксировано в целевых тестах.
- Самостоятельные программы автора включены в общий список «Задания» в рамках сервиса `WorkItem`; не считать это незакрытой задачей. Ссылка из общего списка открывает `/objects/urza/{id}?tab=programs`, сохраняя контекст дерева объектов.
- В таблице общего списка «Задания» намеренно показывается ссылка «Открыть», а не все действия `WorkItem`. Действие «Отправить на согласование» доступно в карточке задания. ### Задания: результат последней работы

Пользователь вручную подтвердил следующие сценарии после изменений:

- переназначенное задание исчезает из списка прежнего исполнителя;
- новый исполнитель видит задание;
- руководитель продолжает видеть задания в пределах своей области доступа;
- карточка показывает текущего исполнителя;
- основной срок задания при переназначении сохраняется;
- результат программы отображается только при наличии результата;
- прежний исполнитель получает отказ в доступе при открытии переназначенного задания по прямому URL;
- новый исполнитель открывает задание;
- руководитель открывает задания в своей области доступа.

Техническое поведение:

- в списке задач для `ENGINEER` показывать только задачи, где `task.assigned_to == current_user.id`;
- общий `_get_accessible_task()` получает `current_user`, проверяет существование активного задания, `AccessService.can_access_urza()` и для `ENGINEER` — назначение на текущего пользователя;
- отсутствие доступа к переназначенному заданию возвращает 403;
- для отображения результата программы используется результат, связанный с `task_id`; удалённый/архивированный результат не показывается.

## 22. Статусы самостоятельных документов и согласование (решение 13.10.2026)

Самостоятельные документы, изменяемые инженером без предварительного `Task`, должны проходить собственный цикл согласования. По возможности использовать существующий `DocumentStatus` и существующие сервисные паттерны.

Базовый цикл документа:

```text
DRAFT → UNDER_REVIEW → APPROVED
             └── возврат на исправление → DRAFT
```

Размещение статуса:

- `TORecord` — статус записи ТО;
- `OTDVersion` — статус конкретной версии ОТД;
- `RZAInstructionVersion` — статус версии инструкции РЗА подстанции;
- `SelectivitySchemeVersion` — статус версии схемы селективности подстанции.

Правила реализации:

1. Любое изменение схемы БД оформлять Alembic-миграцией.
2. Не назначать существующим записям `DRAFT` или `APPROVED` массово без обоснованного backfill по их фактическому состоянию.
3. Статус версии не заменяет `Task.status`. Для документа, связанного с заданием, сохранять существующий workflow `Task` и не дублировать результат как самостоятельную работу.
4. Не удалять и не перезаписывать исторические версии документов.
5. Переходы согласования выполнять через application/service слой; проверять роль, доступ к объекту и область ответственности. Не реализовывать authorization только в маршруте или шаблоне.
6. «На проверке» включает самостоятельные записи, ожидающие решения, только если текущий пользователь вправе выполнить approve/return.
7. `Inspection` сохраняет отдельный workflow; не подключать его к общему `DocumentStatus` автоматически.
8. Основные сведения подстанции роли `ADMIN`, `MANAGER`, `SUPERADMIN` редактируют напрямую в рамках своих прав доступа, без согласования и статуса утверждения.
9. Не выполнять широкий рефакторинг. Вносить минимальные изменения по этапам, сообщать, какие файлы изменены и какие команды реально запускались. Не утверждать, что тесты пройдены, если они не запускались.

### 19.2. Решения и технические ограничения по очистке файлов

1. При ожидаемом `ValueError`, означающем отказ бизнес-операции с отображением формы, сохраняется существующее поведение: загруженные файлы архивируются, а не удаляются.
2. При неожиданном исключении, когда операция не завершилась, загруженные в рамках этой операции объекты удаляются из object storage как компенсационная очистка.
3. `discard_upload()` удаляет бинарный объект по `s3_key`, но не удаляет метаданные `File` из БД. Согласованность метаданных зависит от транзакционного поведения запроса: при исключении ожидается rollback DB-транзакции. При изменении transaction lifecycle это предположение необходимо проверить отдельно.
4. Ошибка компенсационной очистки должна логироваться, но не заменять исходное исключение.
5. Не расширять эту локальную правку до общего рефакторинга file storage или транзакций без отдельного анализа. Взаимодействие object storage и PostgreSQL не является единой атомарной транзакцией; возможность orphan-объектов остаётся отдельным техническим риском.

## 20. Обязательные ограничения на БД, миграции и Git/GitHub

Этот раздел имеет приоритет над любыми общими инструкциями выше, включая стандартный процесс миграций из раздела 4 и команды Git из раздела 16.

### 20.1. Изменения базы данных — только с отдельным согласием

Без явного согласия пользователя на конкретную операцию и конкретный контур запрещено выполнять команды или действия, изменяющие состояние БД или миграций, в том числе:

- `alembic upgrade`, `alembic downgrade`, `alembic stamp` и другие операции, меняющие текущую ревизию;
- применение миграций к любой БД, включая тестовую `rzadb_test`;
- сброс, пересоздание или очистку БД, схем, таблиц либо данных;
- destructive SQL (`DROP`, `TRUNCATE`, массовые `DELETE`) и скрипты массового изменения данных.

Создавать и редактировать файл миграции в рамках согласованной задачи разрешено. Разрешение на подготовку миграции не означает разрешения на её применение. После подготовки нужно проверить `upgrade()`/`downgrade()`, перечислить последствия и предложить команду применения, затем остановиться и дождаться отдельного явного согласия.

### 20.2. Проверка БД перед тестами

Перед запуском тестов, которые могут подключаться к БД, сначала установить фактическую конфигурацию подключения и убедиться, что используется предназначенная тестовая БД. Если контур не подтверждён или есть риск затронуть development/staging/production, не запускать такие тесты до уточнения. Не предполагать, что переменная окружения, имя БД или pytest fixture безопасны, не проверив конфигурацию.

Read-only проверка конфигурации и ревизий допустима, если она не раскрывает секреты и не меняет состояние. Не выводить пароли, токены и полные секретные DSN в логи или отчёт.

### 20.3. Согласованность тестовой и production БД

Различие ревизий между тестовой и production БД само по себе не является поводом немедленно запускать миграцию. Сначала:

1. установить текущую ревизию каждой БД безопасными read-only средствами;
2. сравнить ревизии с `migrations/versions/` и ожидаемым Alembic head;
3. проверить миграцию на предмет потери данных, обратной совместимости и порядка развёртывания;
4. составить план выравнивания с учётом версии приложения, резервной копии и возможности отката;
5. отдельно согласовать применение к каждому контуру.

Не применять миграцию к production автоматически ради выравнивания с тестовой БД. Не откатывать тестовую БД автоматически только ради совпадения ревизий. Если новая версия кода требует ещё не применённой миграции, не развёртывать эту версию на соответствующем контуре до согласованного применения миграции.

### 20.4. Git и GitHub

Без отдельного прямого указания пользователя запрещено выполнять `git commit`, `git push`, изменять/создавать ветки, создавать или изменять PR, а также совершать любые записи в GitHub. Можно читать код и историю GitHub, анализировать diff и предлагать команды. Не выполнять разрушительные команды (`git reset --hard`, `git checkout -- .`, удаление незакоммиченных изменений) без отдельного согласия.

### 20.5. Принцип остановки

Если следующий шаг меняет состояние БД, файлов с данными, миграций в БД или Git/GitHub и точное разрешение на него не получено, остановиться до выполнения. В отчёте явно различать: подготовлено, проверено read-only, выполнено с разрешения; не заявлять о применении или проверке, если они фактически не выполнялись.

### 28.2. События внутренних уведомлений — согласовано 31.10.2026

`TaskHistory` остаётся аудитом бизнес-событий. Пользовательское состояние прочтения хранится отдельно в `TaskNotification`.

Матрица событий и адресатов:

1. **Первичное назначение (`assigned`)** — уведомление новому исполнителю.
2. **Успешный отказ (`rejected`)** — уведомление руководителю, который фактически выполнил назначение задания. Адресата определять по соответствующей записи `TaskHistory` назначения и её `actor_id`, а не автоматически по `Task.created_by`. Создавать уведомление только после успешного отказа.
3. **Переназначение (`reassigned`)** — два отдельных уведомления: прежнему исполнителю об отмене назначения и новому исполнителю о назначении. Получателей брать из `previous_assignee_id` и `new_assignee_id` события `TaskHistory`.
4. **Существенное изменение задания** — текущему исполнителю при изменении срока, описания или существенных условий, влияющих на выполнение. Одно сводное уведомление на одну бизнес-операцию. Перед реализацией найти фактический маршрут и сервис редактирования; не выдумывать отсутствующий workflow. Приоритет учитывать только если соответствующее поле существует в актуальной модели и его значимость отдельно подтверждена.
5. **Возврат на доработку (`review_rejected`)** — текущему исполнителю. Уведомление сообщает о возврате задания на доработку и включает комментарий руководителя, если он указан.

Не создавать уведомления:
- при принятии задания самим исполнителем;
- при завершении/закрытии задания;
- о приближении дедлайна или просрочке.

Действие пользователя не должно создавать уведомление самому этому пользователю. Не рассылать уведомления всем менеджерам предприятия вместо руководителя, фактически выполнившего назначение. Не дублировать внутренние уведомления по email или Telegram.

### 28.3. Модель и жизненный цикл уведомления

Минимальная модель `TaskNotification`:

```text
TaskNotification
├── id: UUID7 primary key
├── task_history_id: FK → TaskHistory
├── recipient_id: FK → User
├── created_at
└── read_at: nullable
```

Правила модели:
- Одна запись соответствует одному событию `TaskHistory` и одному получателю. Для двух получателей создаются две независимые записи.
- Рассмотреть/добавить уникальность `(task_history_id, recipient_id)` для защиты от дублей одного события одному получателю.
- Не дублировать в уведомлении текст, заголовок, URL, статус или иные данные задания: представление формируется из `TaskHistory` и связанного `Task`.
- Не вводить `closed_at`, `is_active` и ручное закрытие/архивирование.
- Новое самостоятельное событие по тому же заданию может создавать новое уведомление; уникальность по `task_id` запрещена.
- Уведомления физически не удаляются.

Lifecycle и безопасность:
- Новое уведомление входит в список непрочитанных и увеличивает счётчик.
- Открытие списка не отмечает уведомления прочитанными.
- Переход по ссылке конкретного уведомления отмечает его прочитанным на сервере. Повторный переход не меняет счётчик повторно.
- Прочитанное уведомление исчезает из списка непрочитанных. Отдельный список прочитанных в MVP не нужен.
- Отказ и переназначение не закрывают и не удаляют старые уведомления автоматически; `read_at` отражает только факт прочтения.
- Пользователь может читать и отмечать прочитанными только собственные уведомления (`recipient_id`). Переход к заданию проходит обычную серверную проверку доступа.
- Защититься от prefetch/link previews: простой GET списка или ссылки не должен сам по себе отмечать уведомление прочитанным. Выбрать безопасный HTTP flow с учётом CSRF и существующих соглашений проекта.
- Уведомление создаётся только после успешной бизнес-операции. Изменение `Task`, запись `TaskHistory` и создание `TaskNotification` выполняются атомарно в существующей транзакции. Репозитории не делают `commit()`.
- Индексы выбирать по фактическим запросам; как минимум обеспечить эффективную выборку непрочитанных уведомлений получателя.

## 30. Внутренние уведомления TaskNotification — реализация завершена (31.10.2026)

Этот раздел дополняет согласованные требования из §28.2–28.3 фактическим результатом реализации. Не возвращать внутренние уведомления в TODO без обнаруженного дефекта или нового требования.

### Реализовано

- Модель `TaskNotification` с UUID7, ссылкой на `TaskHistory`, получателем `User`, `created_at` и nullable `read_at`.
- Уникальность пары `(task_history_id, recipient_id)`; отдельные уведомления одному заданию при разных событиях допускаются.
- Создание уведомлений в рамках существующей транзакции бизнес-операции; repository не выполняет самостоятельный `commit()`.
- События и адресаты:
  - `assigned` — новый исполнитель;
  - `rejected` — руководитель, который фактически назначил задание; источник — actor записи истории назначения, а не `Task.created_by`;
  - `reassigned` — прежний исполнитель и новый исполнитель получают отдельные уведомления;
  - `review_rejected` — текущий исполнитель, с комментарием руководителя при его наличии.
- Не создаются уведомления при принятии, завершении/закрытии, приближении дедлайна или просрочке.
- Не создаются уведомления пользователю за его собственное действие.
- В уведомлении не дублируются данные задания; представление формируется из `TaskHistory` и связанных сущностей.
- Реализованы список непрочитанных, счётчик и безопасное отмечание конкретного уведомления прочитанным. Само открытие списка не отмечает уведомления прочитанными; повторное отмечание не должно повторно уменьшать счётчик.
- Доступ к уведомлениям ограничен их получателем; переход к заданию использует обычную проверку доступа.
- Для асинхронного ORM-загрузки связей учтён `selectinload`, чтобы избежать неявной загрузки и `MissingGreenlet`.

### Детали интерфейса

- Для события `reassigned` текст зависит от адресата:
  - прежнему исполнителю — «Задание снято с вас»;
  - новому исполнителю — «Вам назначено задание».
- Для события `rejected` в представлении показывается имя исполнителя/автора события, если оно доступно.
- Содержание уведомления берётся из истории и связанного задания, без копирования полей задания в `TaskNotification`.

### Дополнительные проверки бизнес-логики

- Проверен `TaskRepository.get_assignment_actor()`: учитывается последнее событие `assigned`/`reassigned`; при переназначении actor возвращается только для актуального нового исполнителя.
- Добавлены тесты на отсутствие истории назначения, обычное назначение, актуальное переназначение и несовпадение исполнителя.
- Добавлен граничный тест: после успешного отказа уведомление руководителю не создаётся, если actor первоначального назначения определить не удалось.
- В тесте отказа используется `configure_available_assignee(...)`, чтобы тестовый исполнитель был зарегистрирован в fake repositories и проходил обычные проверки сервиса.
