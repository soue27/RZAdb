Главное правило: **не добавлять новые сущности, поля, связи или бизнес-правила без отдельного доменного решения пользователя.**

## 10. Files

Бинарные файлы не хранить в PostgreSQL.

Целевой storage: S3-compatible object storage.

Не использовать универсальную полиморфную связь:

```text
File(owner_type, owner_id)
```

Использовать явные FK от доменных сущностей к `files.id`.

Целевой общий механизм:

```text
пользователь
→ AccessService
→ доменный объект
→ FileAccessService
→ File
→ ObjectStorage
→ Просмотр / Скачать
```

### Принятые решения по file access

- `AccessService` остаётся источником истины для прав на доменные объекты.
- `FileAccessService` определяет, имеет ли пользователь право читать конкретный `File` через его владельца.
- `FileOwnerResolver` определяет владельца по существующим явным FK; полиморфные `owner_type/owner_id` не вводятся.
- Один `File` должен иметь одного однозначного владельца. Несколько ролей файлов у одного владельца допустимы.
- Если у `File` несколько разных владельцев, состояние считается неоднозначным и доступ запрещается как техническая ошибка.
- Orphan-файл без владельца не доступен обычному пользователю; очистка orphan-файлов — отдельная будущая операция.
- Архивирование владельца не блокирует доступ к его файлам, если сам пользователь имеет право просматривать архивный объект.
- Архивированный сам `File` недоступен через обычные read routes.
- Для `Inspection` владелец файла определяется через `Inspection.substation_id`.
- Отдельная авторизация через `InspectionTask` для уже созданного результата осмотра не требуется.
- Просмотр и скачивание используют один общий защищённый механизм; PDF viewer не требуется.
- Не создавать отдельные несогласованные file routes для каждой сущности.

### Текущее состояние

Уже реализованы и проверены:

- `FileOwnerResolver`;
- `FileAccessService`;
- защищённые routes просмотра и скачивания;
- проверки аутентификации, владельца, архивного `File`, orphan и ambiguous ownership.

Следующая работа с файлами — **write/UI**: загрузка, привязка и действия с файлами в документных вкладках URZA.

### Задания: результат последней работы

Пользователь вручную подтвердил следующие сценарии после изменений:

- переназначенное задание исчезает из списка прежнего исполнителя;
- новый исполнитель видит задание;
- руководитель продолжает видеть задания в пределах своей области доступа;
- карточка показывает текущего исполнителя;
- основной срок задания при переназначении сохраняется;
- результат программы отображается только при наличии результата;
- прежний исполнитель получает отказ в доступе при открытии переназначенного задания по прямому URL;
- новый исполнитель открывает задание;
- руководитель открывает задания в своей области доступа.

Техническое поведение:

- в списке задач для `ENGINEER` показывать только задачи, где `task.assigned_to == current_user.id`;
- общий `_get_accessible_task()` получает `current_user`, проверяет существование активного задания, `AccessService.can_access_urza()` и для `ENGINEER` — назначение на текущего пользователя;
- отсутствие доступа к переназначенному заданию возвращает 403;
- для отображения результата программы используется результат, связанный с `task_id`; удалённый/архивированный результат не показывается.

Следующий обязательный шаг — проверить, что эти сценарии закреплены регрессионными тестами, и запустить тесты после последних изменений. Не переделывать рабочую реализацию без найденного дефекта.

## 22. Рабочая зона: задания и документы (решение от 12.10.2026)

### Принятая концепция UI

В приложении должны быть разделены два независимых контура работы:

1. **Задания** — работа, порученная руководителем через существующую сущность `Task` и её workflow.
2. **Мои документы** — документы, которые инженер инициирует самостоятельно, без предварительного задания руководителя, и которые могут требовать согласования по правилам соответствующей сущности.

Для руководителя предусматривается отдельная рабочая вкладка **«На проверке»** — список доступных ему заданий и самостоятельных документов, по которым действительно ожидается его решение.

Предлагаемая структура рабочей зоны:

```text
Рабочая зона
├── Задания
│   ├── Активные
│   └── Завершённые
├── Мои документы
│   ├── Активные
│   └── Завершённые
└── На проверке             # доступно руководителю в рамках его полномочий
```

«Задания», «Мои документы» и «На проверке» — представления UI, а не новые доменные сущности. На первом этапе не создавать универсальную таблицу/модель прямых задач и не добавлять поля в БД ради этой навигации.

### Счётчики и поведение UI

- Рядом с названиями вкладок показывать счётчики активных элементов.
- Внутри «Заданий» и «Моих документов» предусмотреть разделение на «Активные» и «Завершённые».
- Счётчики рассчитываются на сервере с учётом роли, области доступа и назначения пользователя; нельзя считать их только по уже загруженным строкам UI.
- Счётчик «На проверке» должен отражать только доступные текущему руководителю элементы, по которым требуется его решение.
- Не допускать дублирования одного результата в рамках одного списка из-за связи документа с `Task`.
- Нулевые состояния списков должны иметь понятное сообщение; просрочку при необходимости показывать отдельно от общего количества.
- После выполнения действия данные/счётчики должны обновляться. Сохранять разумное поведение фильтров и возврата из карточки.
- Визуальное оформление счётчиков и вкладок не должно менять бизнес-логику или права доступа.

### Архитектурные ограничения

- Не переписывать существующий `TaskService` и workflow ради нового UI.
- `Task` управляет процессом выполнения поручения; документ управляет собственным жизненным циклом и версиями.
- Не унифицировать статусы разных доменных сущностей. «Активные» и «Завершённые» — категории интерфейса, а не новые универсальные DB-статусы.
- Сохранять существующие сервисы документов и их `get_available_actions`/эквивалентные правила действий.
- Авторизация централизуется через `AccessService` и действующие проверки конкретных сервисов.
- `Inspection`/«Осмотры» остаётся отдельным процессом и не включается автоматически в `Task` или «Мои документы».
- Не добавлять сущности, поля, связи, миграции или переходы статусов без отдельного доменного решения.

### Реализация поэтапно

1. Сначала проверить фактический код, состояние ветки и существующие тесты; не запускать повторный широкий аудит Codex без реальной необходимости.
2. Не менять существующий список `/tasks` больше необходимого.
3. Создать UI-представление «Мои документы», начав с уже существующего сценария самостоятельных программ на проверке, если текущий код и правила доступа это подтверждают.
4. Добавлять другие типы документов только после определения для каждого типа правил включения в активные/завершённые списки и роли пользователя.
5. Добавить вкладку «На проверке» для руководителя с учётом реальных прав и требуемого действия.
6. Покрыть тестами фильтрацию по роли/доступу, счётчики, отсутствие дублей и перемещение между активным и завершённым представлениями.
7. Сначала выполнять адресные тесты затронутых модулей, затем полный `uv run pytest -q`, если окружение позволяет. Сообщать только о фактически запущенных проверках.

Названия и разделение согласованы на уровне UX-концепции. Точный состав активных/завершённых состояний для каждой сущности требует проверки её действующей модели и сервиса; не выводить его только из названия enum.
