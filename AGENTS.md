## 1. Назначение проекта

RZAdb --- внутреннее веб-приложение для учёта оборудования РЗА,
формуляров, документов, заданий и фактически выполненных работ.

Основная иерархия:

``` text
Холдинг
└── Филиал
    └── Производственное отделение (ПО)
        └── Подстанция
            └── Присоединение
                └── УРЗА
```

Отдельные домены уровня ПС: - схемы селективности; - инструкции по
РЗА; - инспекции ПС.

Инспекция ПС --- отдельный домен и не является обычным Task.

## 3. Архитектурные принципы

-   Разделять `domain/model`, `repositories`, `services`, API и UI.
-   Бизнес-правила не размещать в Jinja-шаблонах или роутерах.
-   Доступ централизовать через `AccessService`.
-   Для критичных операций сохранять аудит.
-   Использовать soft delete там, где это предусмотрено.
-   Файлы не хранить в PostgreSQL: БД хранит метаданные, содержимое ---
    object storage.
-   Не использовать полиморфный `File(owner_type, owner_id)`, если
    возможны обычные FK.
-   Использовать UUID7 через `uuid6`.
-   Workflow-статусы --- Python `StrEnum`.
-   Не добавлять сущности и поля без доменного решения.
-   Версионируемые документы не перезаписывают старые версии.
-   `hot/cold` storage не меняет доменную сущность и историю файла.
-   Нетипичную бизнес-логику выносить в services.
-   В нетривиальных функциях оставлять короткие комментарии «что и
    зачем».
-   Не комментировать очевидный код и простые модели без необходимости.
-   Не дублировать уже реализованные доменные модели.
-   Не смешивать authentication, authorization и domain business rules.

## 7. Authentication

Authentication и authorization разделены.

### Authentication

Используется: - email + password; - `UserRepository.get_by_email()`; -
`PasswordService`; - `AuthService`; - Argon2 через `pwdlib`.

`AuthService` должен возвращать `User` только если: - пользователь
найден; - `active=True`; - `deleted_at is None`; - пароль корректен.

Для всех неуспешных случаев используется единая ошибка
`InvalidCredentialsError`.

### Session

Для MVP и рабочего внутреннего продукта согласован **вариант A ---
signed cookie session**.

Не использовать JWT без отдельного решения.

Cookie: - `HttpOnly`; - `SameSite=Lax`; - `Secure=True` при HTTPS; -
секрет из `SESSION_SECRET`.

В cookie не хранить чувствительные данные и права как источник истины.

Бизнес-логика не должна зависеть от конкретной реализации session
storage.

Будущая замена на server-side sessions, AD/LDAP/SSO должна быть возможна
без переписывания `AuthService` и `AccessService`.

Текущее состояние: - `UserRepository.get_by_email()` --- реализован; -
`PasswordService` --- реализован; - `AuthService` --- реализован; -
application tests authentication --- зелёные; - HTTP
login/logout/session middleware --- следующий блок.

### ObjectStorage

Интерфейс:

``` text
ObjectStorage
├── LocalObjectStorage
└── YandexS3ObjectStorage
```

Сейчас используется `LocalObjectStorage` для dev/test.

Путь dev: `data/uploads/`.

Целевой production storage --- S3-compatible, в том числе Yandex S3.

`FileService` не должен зависеть от конкретного storage backend.

S3 key генерируется приложением.

При переходе hot → cold: - `File.id` не меняется; - доменная история не
меняется; - целостность должна быть проверена до удаления hot-копии.

## 18. Иерархия

`Enterprise`: - Holding; - Branch; - Production Department.

## 19. Task

Одно задание --- один тип работы с одной URZA.

Типы: - OTD; - SETTINGS; - SCHEMES; - MAINTENANCE; - PROGRAM.

Workflow:

``` text
CREATED → ASSIGNED → IN_PROGRESS → COMPLETED → UNDER_REVIEW → CLOSED
```

Дополнительно: - ASSIGNED → REJECTED; - UNDER_REVIEW → IN_PROGRESS.

Причина обязательна при reject/return.

Срок выполнения --- 7 дней.

Acceptance deadline --- 1 день от назначения.

Продление не предусмотрено.

Переназначение не пересчитывает deadline.

Просроченность --- состояние, не отдельный статус.

## 20. Результат Task

## 30. UI/UX

### Общий принцип

RZAdb использует server-rendered UI на базе:

- FastAPI
- Jinja2
- HTMX
- Bootstrap 5
- Material Icons
- Roboto

SPA не используется.

Бизнес-логика, правила доступа и проверки разрешений не размещаются
в Jinja2-шаблонах или JavaScript.

Основная логика:

Domain → Application → Presentation → Jinja2/HTMX.

Bootstrap используется как основной UI-фреймворк.
Собственный CSS допускается только для небольших проектных
доработок, которые невозможно или нецелесообразно реализовать
средствами Bootstrap.

### Основной layout

Интерфейс состоит из:

1. верхней панели;
2. компактной панели статистики;
3. левой навигационной панели;
4. основной области содержимого.

Левая панель содержит дерево:

Holding
→ Branch
→ Production Department
→ Substation
→ Connection
→ URZA

Пользователь видит только ту часть дерева, которая соответствует
его области доступа.

После входа дерево находится в свернутом состоянии.

Выбор объекта не закрывает дерево.

### Sidebar

Sidebar:

- имеет изменяемую ширину;
- может полностью сворачиваться;
- состояние ширины и сворачивания сохраняется между посещениями;
- на мобильных устройствах превращается в компактную/drawer-навигацию.

Над деревом располагается полнотекстовый поиск.

Поиск выполняется только среди доступных пользователю объектов.

При нахождении объекта:

- объект выделяется;
- дерево автоматически раскрывается до найденного объекта;
- родительские элементы становятся видимыми.

### Поиск

Поддерживаются следующие основные поля поиска:

Enterprise:

- полное наименование;
- краткое наименование;
- SAP.

Substation:

- диспетчерское наименование;
- SAP;
- ASUREO;
- адрес.

Connection:

- диспетчерское наименование;
- SAP;
- ASUREO.

URZA:

- диспетчерское наименование;
- инвентарный номер;
- при наличии — обозначение по схеме.

### Верхняя панель

Topbar содержит:

- логотип/название приложения;
- меню заданий;
- индикатор уведомлений;
- имя пользователя;
- роль пользователя;
- переключатель светлой/тёмной темы;
- выход.

Меню заданий показывает активные задания пользователя.

Уведомления имеют компактное представление и могут вести
на страницу заданий.

### Тема

Используются:

- светлая тема;
- тёмная тема.

По умолчанию выбирается системная тема через
`prefers-color-scheme`.

Пользователь может вручную изменить тему.

Выбранная тема сохраняется между посещениями.

### Статистика

Под topbar располагается компактная панель статистики.

Минимальные показатели:

- активные задания;
- просроченные задания;
- задания на проверке;
- другие показатели, относящиеся к роли пользователя.

Показатели кликабельны.

Переход по показателю открывает соответствующий
отфильтрованный список.

Статистика предоставляется сервером и учитывает права доступа пользователя.

### Навигация по объектам

При выборе объекта соответствующего уровня отображается его карточка:

- Enterprise/ПО — карточка предприятия и статистика;
- Substation — карточка подстанции и дочерние объекты;
- Connection — карточка присоединения и список URZA;
- URZA — полная карточка устройства.

Основной порядок идентификации URZA:

Substation → Connection → URZA.

Дерево является основной навигацией.

Breadcrumbs являются вспомогательной навигацией и могут
отображаться в нижней части карточки.

### Карточка URZA

В верхней части карточки отображаются:

- идентификация устройства;
- статус;
- основные сведения.

Статус всегда отображается одновременно:

- текстом;
- иконкой;
- цветом.

Цвет не является единственным способом передачи состояния.

Основные действия URZA размещаются в нижней части карточки.

Возможные действия:

- Изменить;
- Добавить запись;
- Архивировать.

Доступность действий определяется backend-проверкой прав.

UI может скрывать недоступные пользователю действия,
но backend всегда выполняет повторную проверку.

Редактирование URZA выполняется на отдельной странице.

После сохранения пользователь возвращается на карточку URZA.

### Вкладки URZA

Порядок вкладок фиксирован:

1. ОТД
2. Уставки
3. Схемы
4. ТО
5. Программы
6. Инструкция

Для вкладок, где это уместно, допускаются счётчики записей.

Счётчики размещаются в нижней части содержимого вкладки,

### История

Для ОТД, Программ и Инструкций используется модель:

- отображение текущей версии;
- основное действие;
- кнопка «Смотреть историю»;
- история версий отдельным списком/таблицей;
- версии сортируются по датам.

Для остальных разделов исторические записи отображаются
не отдельными карточками, а в виде реестровых таблиц,
отсортированных по дате.

Для повторяющихся записей используется табличное представление.

Например, вкладка ТО:

| 26.06.2016 | К | Не выявлено | Инженер СРЗА Балаев С.В. |

### Карточка подстанции

Карточка подстанции содержит:

- основные сведения;
- присоединения;
- инспекции;
- инструкции;
- схемы селективности.

Инспекции являются отдельным PS-level доменом и
не отображаются как часть ТО на уровне URZA.

Выбор присоединения в таблице подстанции автоматически
раскрывает дерево до выбранного присоединения.

### Задания

Задания имеют отдельную страницу с таблицей.

Предусматриваются фильтры:

- Все;
- Мои;
- В работе;
- На проверке;
- Просроченные.

При переходе из задания к связанному URZA:

- открывается карточка соответствующего URZA;
- дерево автоматически раскрывается до устройства;
- при необходимости открывается соответствующая вкладка URZA.

Страница задания при этом остаётся доступной.

### Архив

Для пользовательских действий используется термин
«Архивировать», а не «Удалить».

Архивированные объекты не удаляются физически.

Архив отображается в конце дерева подстанций.

### Формы

Сложные формы создания и редактирования реализуются
на отдельных страницах.

Modal используется для:

- подтверждений;
- предупреждений;
- коротких операций.

Редактирование сложных сущностей через modal не используется.

### Empty states

Пустое состояние должно содержать:

1. понятное пользователю объяснение;
2. действие, если действие возможно.

Например:

> Записей ТО пока нет.

> [Добавить запись ТО]

Не использовать пустые области без объяснения.

### HTMX

HTMX используется для:

- поиска;
- фильтрации;
- пагинации;
- обновления отдельных частей страницы;
- небольших inline-операций.

Индикатор загрузки отображается только внутри
изменяемой области.

Полная перезагрузка страницы используется там,
где она проще и понятнее.

### Ошибки

Ошибки отображаются:

- общим alert в верхней части области;
- ошибками непосредственно возле соответствующих полей формы.

Пользовательские сообщения должны быть понятными,
без необходимости читать traceback.

### Адаптивность

Интерфейс проектируется desktop-first, но должен
корректно работать на планшетах и мобильных устройствах.

Sidebar на небольших экранах переходит в компактный/drawer-режим.

Широкие таблицы должны иметь возможность горизонтального
прокручивания либо адаптированного представления.
