# AGENTS.md — База данных РЗА

## 1. Назначение проекта

Проект — веб-приложение для учёта оборудования РЗА, формуляров, документов и выполнения работ по УРЗА.

Основная иерархия:

Холдинг
└── Филиал
    └── Производственное отделение (ПО)
        └── Подстанция
            └── Присоединение
                └── УРЗА

## 2. Технологический стек

- Python 3.13
- FastAPI
- Jinja2
- HTMX
- PostgreSQL
- SQLAlchemy 2.x, async
- Alembic
- Pydantic
- S3-compatible object storage
- aioboto3
- Docker
- GitHub Actions
- structlog

Текущая архитектура должна оставаться простой для сопровождения, но соответствовать хорошим практикам production-разработки.

## 3. Архитектурные принципы

- Разделять domain/model, repositories, services, API и UI.
- Бизнес-правила не размещать в Jinja-шаблонах или роутерах.
- Доступ централизовать через AccessService.
- Для критичных операций сохранять аудит.
- Использовать soft delete там, где это предусмотрено моделью.
- Файлы не хранить в PostgreSQL: PostgreSQL хранит метаданные и ссылки, содержимое — в S3.
- Не использовать полиморфную связь File(owner_type, owner_id), если можно обеспечить обычные FK.
- Использовать UUID7 через пакет uuid6.
- Справочные сущности, где нужна гибкость, хранить в БД; статусы workflow — Python Enum.
- Не добавлять сущности и поля без необходимости: сначала фиксировать доменное решение, затем реализацию.

## 4. Идентификация и аудит

Общие служебные поля сущностей:

- id
- created_at
- created_by
- updated_at
- updated_by
- deleted_at
- deleted_by

`created_by`/`updated_by` в текущей реализации не имеют FK на users из-за циклической зависимости.

Для критичных операций используется audit log.

## 5. Доступ и роли

Роли:

- Суперадмин
- Специалист
- Администратор
- Руководитель
- Инженер

Общее правило: все пользователи, кроме суперадмина, работают только в пределах своего предприятия и его подчинённых объектов.

Привязка:

- Специалист — Холдинг или Филиал.
- Администратор — Производственное отделение.
- Руководитель — Производственное отделение.
- Инженер — Производственное отделение.
- Суперадмин — без ограничения предприятием.

Права:

- Специалист: просмотр и скачивание документов.
- Администратор: создание и изменение объектов и данных, удаление — по правилам подтверждения.
- Руководитель: управление иерархией, создание/назначение заданий, проверка результатов.
- Инженер: выполнение заданий и работа с формулярами; не изменяет иерархию.
- Суперадмин: полный доступ.

## 6. Формуляры и документы

Для УРЗА существуют пять отдельных доменов:

1. ОТД
2. Уставки
3. Схемы
4. ТО
5. Программы

Формуляр — логический контейнер. Запись — конкретное событие/операция.

Не объединять эти пять доменов в одну универсальную таблицу.

Файлы хранятся в S3. В БД — File и явные FK из доменных сущностей.

Автоматические имена файлов должны строиться по контексту ПС/присоединения/УРЗА/типа документа/даты. Пользователь не должен вручную задавать системное имя файла.

## 7. Workflow заданий

Задание:

- создаётся руководителем или суперадмином;
- назначается инженеру;
- инженер принимает или отклоняет;
- после принятия сразу переходит в «В работе»;
- инженер после выполнения требований формуляра переводит в «Работа выполнена»;
- руководитель проверяет;
- может подтвердить или отправить на доработку;
- после подтверждения задание закрыто.

При отклонении инженером причина обязательна. Руководитель получает уведомление и может назначить задание повторно.

При отправке на доработку причина обязательна. Инженер получает уведомление, после чего задание сразу возвращается в «В работе», без повторного принятия.

Просроченное задание не получает отдельного контроля. Оно продолжает обычный workflow.

Дедлайн выполнения сейчас — 7 дней от создания. Продление не предусматривается.

Срок принятия задания — 1 день от назначения инженеру. Если инженер не принял/отклонил, руководителю отправляется уведомление; статус остаётся «Назначено инженеру».

Переназначение разрешено, пока задание находится в «Назначено инженеру». Дедлайн при переназначении не меняется.

## 8. Результат задания

Нельзя завершить задание просто нажатием кнопки.

Перед «Работа выполнена» система автоматически проверяет обязательные действия и документы, зависящие от типа работы.

Инженер должен внести соответствующую запись в формуляр и загрузить необходимые документы.

Если работа выполнена вне задания, `task_id` у записи формуляра может быть NULL.

Если запись создана в рамках задания, `task_id` устанавливается автоматически.

## 9. Уведомления

В приложении используется колокольчик рядом с логином.

Email используется для:

- уведомления о поступившем задании инженеру;
- уведомления о поступившем задании руководителю в случаях, когда требуется его действие;
- напоминаний о дедлайне;
- уведомления о просрочке;
- уведомления руководителю о непринятом задании.

Напоминания о дедлайне начинаются за 3 дня и отправляются каждый день до закрытия задания.

При просрочке уведомляются исполнитель и руководитель.

Email-уведомления обязательны и не отключаются пользователем.

Уведомления в приложении хранятся в БД. Непрочитанные выделяются. После просмотра уведомление считается закрытым и убирается из основного списка, но запись в БД сохраняется.

Статистические email-рассылки — второй этап, после первой версии приложения.

## 10. Интерфейс заданий

Для инженера — «Мои задания».

Для руководителя:

- «На проверке» — выполненные задания, ожидающие решения;
- «Активные задания» — все выданные и ещё не закрытые;
- «История заданий» — закрытые задания.

В списках должна быть ссылка на карточку УРЗА.

В «На проверке» руководитель видит:

- ПС;
- присоединение;
- УРЗА;
- тип работы;
- вид ТО, если применимо;
- ФИО инженера;
- ссылку на карточку УРЗА.

## 11. История заданий

Для каждого Task хранится полная неизменяемая история workflow.

История содержит как минимум:

- событие;
- старый статус;
- новый статус;
- пользователя;
- дату/время;
- комментарий/причину при наличии.

История сохраняет создание, назначения, переназначения, принятие, отклонение, просрочку, выполнение, доработку и подтверждение.

Удаление ошибочно созданного задания до начала работы также фиксируется в истории.

## 12. Ограничения первой версии

Не реализовывать сейчас:

- статистическую email-рассылку;
- планирование ТО как часть этого приложения;
- отдельный workflow для просроченных заданий;
- продление дедлайна;
- отдельный контроль просроченных заданий;
- регистрацию пользователей.

Если решение не зафиксировано в документации, не считать его утверждённым — сначала вынести на обсуждение.
