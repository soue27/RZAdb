# AGENTS.md — RZAdb / База Данных РЗА

## 1. Назначение

RZAdb — внутреннее веб-приложение для учёта оборудования РЗА, подстанций, присоединений, устройств РЗА, технической документации, формуляров, уставок, схем, ТО, программ, инструкций, осмотров и задач.

Проект некоммерческий.

Этот файл — рабочие инструкции для coding agents. `DATABASE_DESIGN.md` фиксирует согласованные доменные и архитектурные решения.

Главное правило: **не добавлять новые сущности, поля, связи или бизнес-правила без отдельного доменного решения пользователя.**

### `app/presentation/`

FastAPI routes/dependencies, Jinja2 и HTMX.

Бизнес-логику не помещать в templates и routes.

Не смешивать authentication, authorization и domain logic.

### Local-first и независимость от инфраструктуры

Разработка RZAdb должна полноценно продолжаться без заранее купленных VPS,
S3 и других платных внешних ресурсов.

- Текущее локальное окружение: приложение запускается на macOS, PostgreSQL
  установлен непосредственно в macOS.
- Планируемое production-окружение: приложение и PostgreSQL работают в Docker
  на VPS.
- Не переносить PostgreSQL в Docker локально только ради сходства с production.
- Не требовать наличия VPS или S3 для разработки, тестирования и приёмки
  функций, которые можно проверить локально.
- Бизнес-логика не должна зависеть от конкретного способа запуска PostgreSQL
  или физического расположения файлов.
- Различия окружений должны по возможности задаваться конфигурацией и
  инфраструктурными адаптерами, без дублирования бизнес-логики.
- Локальное файловое хранилище используется для разработки; S3-compatible
  storage остаётся целевым вариантом production и подключается позднее.
- Не создавать заглушки и дополнительные абстракции только ради гипотетических
  будущих провайдеров. Сначала определить необходимый контракт, затем
  реализовывать конкретный адаптер при появлении практической потребности.
- Не внедрять платные сервисы до появления реальной необходимости.
- Не усложнять локальную разработку ради точного копирования production.

При проектировании новой инфраструктурной функции сначала определить, что
можно полноценно реализовать и проверить локально, а что следует отложить до
появления VPS/S3.

## 10. Files

Бинарные файлы не хранить в PostgreSQL.

Целевой storage: S3-compatible object storage.

Не использовать универсальную полиморфную связь:

```text
File(owner_type, owner_id)
```

Использовать явные FK от доменных сущностей к `files.id`.

Целевой общий механизм:

```text
пользователь
→ AccessService
→ доменный объект
→ FileAccessService
→ File
→ ObjectStorage
→ Просмотр / Скачать
```

### Принятые решения по file access

- `AccessService` остаётся источником истины для прав на доменные объекты.
- `FileAccessService` определяет, имеет ли пользователь право читать конкретный `File` через его владельца.
- `FileOwnerResolver` определяет владельца по существующим явным FK; полиморфные `owner_type/owner_id` не вводятся.
- Один `File` должен иметь одного однозначного владельца. Несколько ролей файлов у одного владельца допустимы.
- Если у `File` несколько разных владельцев, состояние считается неоднозначным и доступ запрещается как техническая ошибка.
- Orphan-файл без владельца не доступен обычному пользователю; очистка orphan-файлов — отдельная будущая операция.
- Архивирование владельца не блокирует доступ к его файлам, если сам пользователь имеет право просматривать архивный объект.
- Архивированный сам `File` недоступен через обычные read routes.
- Для `Inspection` владелец файла определяется через `Inspection.substation_id`.
- Отдельная авторизация через `InspectionTask` для уже созданного результата осмотра не требуется.
- Просмотр и скачивание используют один общий защищённый механизм; PDF viewer не требуется.
- Не создавать отдельные несогласованные file routes для каждой сущности.

### Текущее состояние

Уже реализованы и проверены:

- `FileOwnerResolver`;
- `FileAccessService`;
- защищённые routes просмотра и скачивания;
- проверки аутентификации, владельца, архивного `File`, orphan и ambiguous ownership.

Следующая работа с файлами — **write/UI**: загрузка, привязка и действия с файлами в документных вкладках URZA.

## 10.1. Резервное копирование PostgreSQL — согласованная архитектура (07.11.2026)

Этот раздел фиксирует принятые решения. Он **не означает, что механизм уже
реализован**. До реализации необходимо изучить существующие SMTP, конфигурацию,
фоновые задачи, файловую инфраструктуру и структуру административного UI.

### Область резервирования

- На текущем этапе самостоятельно резервируется PostgreSQL.
- Бинарные файлы приложения не включаются в отдельную самописную систему
  резервирования на первом этапе.
- Для будущего S3 выбран подход: использовать возможности провайдера —
  репликацию, Versioning и Object Lock, если конкретный провайдер и тариф их
  поддерживают. Отдельное дублирование всех объектов S3 пока не планируется.
- Репликация S3 сама по себе не считается защитой от логического удаления,
  перезаписи или компрометации учётной записи. Versioning и Object Lock
  должны быть проверены по фактическим условиям выбранного провайдера.
- Выбор и покупка VPS, S3 и внешних ресурсов не являются предварительным
  условием для локальной реализации резервирования PostgreSQL.

### Формат и создание дампа

- Использовать `pg_dump` в Custom Format (`-Fc`); восстановление выполнять
  средствами `pg_restore`.
- Дамп не шифровать. Это осознанное решение пользователя.
- Не хранить дампы в Git и не размещать их в публично доступных каталогах.
- После создания проверять код завершения `pg_dump`, наличие и размер файла,
  а также возможность прочитать оглавление дампа через `pg_restore --list`.
- Рассчитывать SHA-256 готового файла для контроля целостности.
- Временные незашифрованные промежуточные файлы, если они появляются,
  удалять после завершения цикла; итоговый дамп остаётся незашифрованным.
- Учитывать, что `pg_dump` отдельной базы не сохраняет глобальные объекты
  PostgreSQL (например, роли и tablespace). Параметры подключения, роли и
  права должны восстанавливаться из конфигурации окружения. Не добавлять
  `pg_dumpall --globals-only` без выясненной необходимости.

### Каналы хранения и конфигурация

Предусмотреть независимые переключатели в настройках окружения (`.env`):

- общий выключатель резервирования;
- локальное сохранение;
- отправка дампа вложением на email суперадминистратора;
- загрузка дампа на Яндекс Диск.

Каждый канал включается и отключается независимо. Ошибка одного канала не
должна отменять остальные. Если канал включён, но его обязательные настройки
отсутствуют или некорректны, это должно отражаться как ошибка соответствующего
канала, а не как успешная операция.

Локальная копия является обязательным рекомендуемым каналом и по умолчанию
должна быть включена. Каталог локальных копий на текущем этапе — `data/backups/`;
в production он должен располагаться на постоянном каталоге/volume хоста,
а не в эфемерном слое контейнера.

Email:
- отправлять сам файл дампа вложением;
- получатель задаётся явно конфигурацией, а не определяется динамически по
  пользовательской роли во время каждого запуска;
- использовать существующую SMTP-инфраструктуру проекта после её проверки;
- учитывать ограничения размера вложений. Превышение лимита — ошибка email-
  канала, не отменяющая локальное сохранение и загрузку на Яндекс Диск.

Яндекс Диск:
- использовать отдельный каталог для резервных копий;
- использовать токен из конфигурации/секретов, не хранить его в Git;
- подтверждать успешную загрузку до очистки старых копий в этом хранилище.

Точные имена переменных `.env`, значения по умолчанию и допустимые диапазоны
должны быть согласованы при реализации с учётом существующего `Settings`.
Не копировать примерные имена переменных из обсуждения без сверки с кодом.

### Расписание и ручной запуск

- Резервирование выполняется ежедневно автоматически.
- Суперадминистратор может запустить тот же сценарий вручную из интерфейса.
- Автоматический и ручной запуск используют один общий механизм резервирования.
- Ручной запуск не должен выполнять длительную операцию внутри HTTP-запроса:
  он запускает фоновую задачу, а UI показывает её состояние.
- Одновременно допускается не более одного активного запуска. Нужна защита
  от параллельного старта из расписания и UI.
- Не привязывать расписание к каждому процессу Uvicorn: при нескольких
  workers это может породить дублирующиеся запуски.
- Конкретный механизм расписания выбирается после изучения текущей реализации
  фоновых задач и целевого способа запуска. Локальное расписание должно
  работать без VPS; на production его можно запускать через подходящий
  механизм Docker/хоста без изменения сценария резервирования.

### Независимость каналов и очистка

- Сначала создать и проверить дамп.
- Каждый включённый канал обрабатывается независимо; фиксировать отдельный
  результат локального сохранения, email и Яндекс Диска.
- Общий запуск может завершиться частичным успехом, если дамп создан, но
  один или несколько каналов доставки завершились ошибкой.
- Очистку старых копий выполнять по количеству последних успешных копий
  отдельно для каждого поддерживаемого файлового хранилища.
- Старые копии удалять только после успешного создания новой копии в
  соответствующем хранилище.
- Не удалять последнюю доступную успешную копию из-за ошибки нового запуска.
- Email не управляется локальной политикой очистки: дальнейшее хранение писем
  определяется почтовым сервисом и почтовым ящиком получателя.
- Значения retention должны быть конфигурируемыми; конкретные значения
  согласовать при реализации, не считать ранее обсуждавшиеся числа
  окончательными.

### История и административный интерфейс

- Отдельную таблицу PostgreSQL для истории резервирования **не создавать**.
- Историю хранить в JSON-манифестах рядом с локальными файлами дампов.
- Манифест должен содержать как минимум дату/время запуска, имя и размер
  дампа, SHA-256, длительность, результат проверки дампа, результаты каждого
  канала и сведения об ошибках.
- Текущий активный запуск можно показывать по состоянию фоновой задачи;
  завершённые запуски — читать из манифестов.
- Не создавать отдельную DB-модель, Alembic migration или самостоятельную
  систему хранения состояния только ради истории резервирования.
- История доступна в пределах фактически сохранившихся манифестов. Потеря
  локального каталога резервирования означает потерю локальной истории;
  отдельная репликация манифестов пока не требуется.

В административном интерфейсе должна быть отдельная страница
«Резервное копирование», доступная только `SUPERADMIN`. Она должна показывать:
- состояние резервирования и время последнего/следующего запуска, если
  расписание позволяет достоверно определить следующее время;
- кнопку ручного запуска;
- состояние текущей операции;
- дату, длительность и размер завершённых дампов;
- SHA-256 и результат проверки;
- отдельные статусы локального сохранения, email и Яндекс Диска;
- историю запусков и ошибки;
- возможность скачать доступный локальный дамп через защищённый route.

Не давать интерфейсу восстановления полномочий на удаление или замену
production-базы. UI для восстановления на данном этапе не согласован.

### Восстановление

- Восстановление выполняется отдельной CLI-процедурой, а не кнопкой
  административного интерфейса.
- Источником может быть локальный дамп, скачанный файл с Яндекс Диска или
  вложение email; после получения используется один и тот же процесс.
- Перед восстановлением проверить формат, размер, SHA-256 (если манифест
  доступен) и читаемость дампа через PostgreSQL tools.
- Безопасный основной сценарий — восстановление в отдельную пустую базу,
  например `rzadb_restore`, без перезаписи действующей базы.
- После восстановления проверить успешность `pg_restore`, наличие ожидаемой
  структуры и возможность подключения приложения.
- Переключение приложения на восстановленную базу — отдельная осознанная
  операция с предварительной проверкой конфигурации и возможностью возврата.
  Не выполнять автоматическое переключение сразу после `pg_restore`.
- Восстановление production требует отдельной процедуры с учётом остановки
  приложения, соединений, ролей и конфигурации Docker Compose.
- Практическая проверка восстановления обязательна для приёмки механизма
  резервирования.

### Безопасность

Дампы не шифруются по решению пользователя и содержат чувствительные данные.
Поэтому:
- ограничить права доступа к локальному каталогу резервных копий;
- исключить его из Git и публичной раздачи;
- не логировать содержимое дампов, SMTP-пароли и токены;
- хранить SMTP credentials и токен Яндекс Диска только в секретах/переменных
  окружения;
- использовать TLS для SMTP и HTTPS для API Яндекс Диска;
- ограничить доступ к почтовому ящику и Яндекс Диску;
- не считать защищённый транспорт заменой защите данных в состоянии покоя.

## 22. Статусы самостоятельных документов и согласование (решение 13.10.2026)

Самостоятельные документы, изменяемые инженером без предварительного `Task`, должны проходить собственный цикл согласования. По возможности использовать существующий `DocumentStatus` и существующие сервисные паттерны.

Базовый цикл документа:

```text
DRAFT → UNDER_REVIEW → APPROVED
             └── возврат на исправление → DRAFT
```

Размещение статуса:

- `TORecord` — статус записи ТО;
- `OTDVersion` — статус конкретной версии ОТД;
- `RZAInstructionVersion` — статус версии инструкции РЗА подстанции;
- `SelectivitySchemeVersion` — статус версии схемы селективности подстанции.

Правила реализации:

1. Любое изменение схемы БД оформлять Alembic-миграцией.
2. Не назначать существующим записям `DRAFT` или `APPROVED` массово без обоснованного backfill по их фактическому состоянию.
3. Статус версии не заменяет `Task.status`. Для документа, связанного с заданием, сохранять существующий workflow `Task` и не дублировать результат как самостоятельную работу.
4. Не удалять и не перезаписывать исторические версии документов.
5. Переходы согласования выполнять через application/service слой; проверять роль, доступ к объекту и область ответственности. Не реализовывать authorization только в маршруте или шаблоне.
6. «На проверке» включает самостоятельные записи, ожидающие решения, только если текущий пользователь вправе выполнить approve/return.
7. `Inspection` сохраняет отдельный workflow; не подключать его к общему `DocumentStatus` автоматически.
8. Основные сведения подстанции роли `ADMIN`, `MANAGER`, `SUPERADMIN` редактируют напрямую в рамках своих прав доступа, без согласования и статуса утверждения.
9. Не выполнять широкий рефакторинг. Вносить минимальные изменения по этапам, сообщать, какие файлы изменены и какие команды реально запускались. Не утверждать, что тесты пройдены, если они не запускались.

## 20. Обязательные ограничения на БД, миграции и Git/GitHub

Этот раздел имеет приоритет над любыми общими инструкциями выше, включая стандартный процесс миграций из раздела 4 и команды Git из раздела 16.

### 20.1. Изменения базы данных — только с отдельным согласием

Без явного согласия пользователя на конкретную операцию и конкретный контур запрещено выполнять команды или действия, изменяющие состояние БД или миграций, в том числе:

- `alembic upgrade`, `alembic downgrade`, `alembic stamp` и другие операции, меняющие текущую ревизию;
- применение миграций к любой БД, включая тестовую `rzadb_test`;
- сброс, пересоздание или очистку БД, схем, таблиц либо данных;
- destructive SQL (`DROP`, `TRUNCATE`, массовые `DELETE`) и скрипты массового изменения данных.

Создавать и редактировать файл миграции в рамках согласованной задачи разрешено. Разрешение на подготовку миграции не означает разрешения на её применение. После подготовки нужно проверить `upgrade()`/`downgrade()`, перечислить последствия и предложить команду применения, затем остановиться и дождаться отдельного явного согласия.

### 20.2. Проверка БД перед тестами

Перед запуском тестов, которые могут подключаться к БД, сначала установить фактическую конфигурацию подключения и убедиться, что используется предназначенная тестовая БД. Если контур не подтверждён или есть риск затронуть development/staging/production, не запускать такие тесты до уточнения. Не предполагать, что переменная окружения, имя БД или pytest fixture безопасны, не проверив конфигурацию.

Read-only проверка конфигурации и ревизий допустима, если она не раскрывает секреты и не меняет состояние. Не выводить пароли, токены и полные секретные DSN в логи или отчёт.

### 20.3. Согласованность тестовой и production БД

Различие ревизий между тестовой и production БД само по себе не является поводом немедленно запускать миграцию. Сначала:

1. установить текущую ревизию каждой БД безопасными read-only средствами;
2. сравнить ревизии с `migrations/versions/` и ожидаемым Alembic head;
3. проверить миграцию на предмет потери данных, обратной совместимости и порядка развёртывания;
4. составить план выравнивания с учётом версии приложения, резервной копии и возможности отката;
5. отдельно согласовать применение к каждому контуру.

Не применять миграцию к production автоматически ради выравнивания с тестовой БД. Не откатывать тестовую БД автоматически только ради совпадения ревизий. Если новая версия кода требует ещё не применённой миграции, не развёртывать эту версию на соответствующем контуре до согласованного применения миграции.

### 20.4. Git и GitHub

Без отдельного прямого указания пользователя запрещено выполнять `git commit`, `git push`, изменять/создавать ветки, создавать или изменять PR, а также совершать любые записи в GitHub. Можно читать код и историю GitHub, анализировать diff и предлагать команды. Не выполнять разрушительные команды (`git reset --hard`, `git checkout -- .`, удаление незакоммиченных изменений) без отдельного согласия.

### 20.5. Принцип остановки

Если следующий шаг меняет состояние БД, файлов с данными, миграций в БД или Git/GitHub и точное разрешение на него не получено, остановиться до выполнения. В отчёте явно различать: подготовлено, проверено read-only, выполнено с разрешения; не заявлять о применении или проверке, если они фактически не выполнялись.

### 28.2. События внутренних уведомлений — согласовано 31.10.2026

`TaskHistory` остаётся аудитом бизнес-событий. Пользовательское состояние прочтения хранится отдельно в `TaskNotification`.

Матрица событий и адресатов:

1. **Первичное назначение (`assigned`)** — уведомление новому исполнителю.
2. **Успешный отказ (`rejected`)** — уведомление руководителю, который фактически выполнил назначение задания. Адресата определять по соответствующей записи `TaskHistory` назначения и её `actor_id`, а не автоматически по `Task.created_by`. Создавать уведомление только после успешного отказа.
3. **Переназначение (`reassigned`)** — два отдельных уведомления: прежнему исполнителю об отмене назначения и новому исполнителю о назначении. Получателей брать из `previous_assignee_id` и `new_assignee_id` события `TaskHistory`.
4. **Существенное изменение задания** — текущему исполнителю при изменении срока, описания или существенных условий, влияющих на выполнение. Одно сводное уведомление на одну бизнес-операцию. Перед реализацией найти фактический маршрут и сервис редактирования; не выдумывать отсутствующий workflow. Приоритет учитывать только если соответствующее поле существует в актуальной модели и его значимость отдельно подтверждена.
5. **Возврат на доработку (`review_rejected`)** — текущему исполнителю. Уведомление сообщает о возврате задания на доработку и включает комментарий руководителя, если он указан.

Не создавать уведомления:
- при принятии задания самим исполнителем;
- при завершении/закрытии задания;
- о приближении дедлайна или просрочке.

Действие пользователя не должно создавать уведомление самому этому пользователю. Не рассылать уведомления всем менеджерам предприятия вместо руководителя, фактически выполнившего назначение. Не дублировать внутренние уведомления по email или Telegram.

### 28.3. Модель и жизненный цикл уведомления

Минимальная модель `TaskNotification`:

```text
TaskNotification
├── id: UUID7 primary key
├── task_history_id: FK → TaskHistory
├── recipient_id: FK → User
├── created_at
└── read_at: nullable
```

Правила модели:
- Одна запись соответствует одному событию `TaskHistory` и одному получателю. Для двух получателей создаются две независимые записи.
- Рассмотреть/добавить уникальность `(task_history_id, recipient_id)` для защиты от дублей одного события одному получателю.
- Не дублировать в уведомлении текст, заголовок, URL, статус или иные данные задания: представление формируется из `TaskHistory` и связанного `Task`.
- Не вводить `closed_at`, `is_active` и ручное закрытие/архивирование.
- Новое самостоятельное событие по тому же заданию может создавать новое уведомление; уникальность по `task_id` запрещена.
- Уведомления физически не удаляются.

Lifecycle и безопасность:
- Новое уведомление входит в список непрочитанных и увеличивает счётчик.
- Открытие списка не отмечает уведомления прочитанными.
- Переход по ссылке конкретного уведомления отмечает его прочитанным на сервере. Повторный переход не меняет счётчик повторно.
- Прочитанное уведомление исчезает из списка непрочитанных. Отдельный список прочитанных в MVP не нужен.
- Отказ и переназначение не закрывают и не удаляют старые уведомления автоматически; `read_at` отражает только факт прочтения.
- Пользователь может читать и отмечать прочитанными только собственные уведомления (`recipient_id`). Переход к заданию проходит обычную серверную проверку доступа.
- Защититься от prefetch/link previews: простой GET списка или ссылки не должен сам по себе отмечать уведомление прочитанным. Выбрать безопасный HTTP flow с учётом CSRF и существующих соглашений проекта.
- Уведомление создаётся только после успешной бизнес-операции. Изменение `Task`, запись `TaskHistory` и создание `TaskNotification` выполняются атомарно в существующей транзакции. Репозитории не делают `commit()`.
- Индексы выбирать по фактическим запросам; как минимум обеспечить эффективную выборку непрочитанных уведомлений получателя.

## 30. Внутренние уведомления TaskNotification — реализация завершена (31.10.2026)

Этот раздел дополняет согласованные требования из §28.2–28.3 фактическим результатом реализации. Не возвращать внутренние уведомления в TODO без обнаруженного дефекта или нового требования.

### Реализовано

- Модель `TaskNotification` с UUID7, ссылкой на `TaskHistory`, получателем `User`, `created_at` и nullable `read_at`.
- Уникальность пары `(task_history_id, recipient_id)`; отдельные уведомления одному заданию при разных событиях допускаются.
- Создание уведомлений в рамках существующей транзакции бизнес-операции; repository не выполняет самостоятельный `commit()`.
- События и адресаты:
  - `assigned` — новый исполнитель;
  - `rejected` — руководитель, который фактически назначил задание; источник — actor записи истории назначения, а не `Task.created_by`;
  - `reassigned` — прежний исполнитель и новый исполнитель получают отдельные уведомления;
  - `review_rejected` — текущий исполнитель, с комментарием руководителя при его наличии.
- Не создаются уведомления при принятии, завершении/закрытии, приближении дедлайна или просрочке.
- Не создаются уведомления пользователю за его собственное действие.
- В уведомлении не дублируются данные задания; представление формируется из `TaskHistory` и связанных сущностей.
- Реализованы список непрочитанных, счётчик и безопасное отмечание конкретного уведомления прочитанным. Само открытие списка не отмечает уведомления прочитанными; повторное отмечание не должно повторно уменьшать счётчик.
- Доступ к уведомлениям ограничен их получателем; переход к заданию использует обычную проверку доступа.
- Для асинхронного ORM-загрузки связей учтён `selectinload`, чтобы избежать неявной загрузки и `MissingGreenlet`.

### Детали интерфейса

- Для события `reassigned` текст зависит от адресата:
  - прежнему исполнителю — «Задание снято с вас»;

- Для события `rejected` в представлении показывается имя исполнителя/автора события, если оно доступно.
- Содержание уведомления берётся из истории и связанного задания, без копирования полей задания в `TaskNotification`.

- Для найденной организации значение `short_name` из Excel должно совпадать с существующим значением после удаления пробелов по краям и сравнения без учёта регистра. Расхождение является ошибкой; автоматическое обновление запрещено.
- Для новой организации сохраняются оба значения: `full_name` и `short_name`.
- Если одна и та же организация указана в нескольких строках с разными `short_name`, импорт отклоняется.
- Сопоставление выполняется последовательно:
  - Holding — по нормализованному `full_name` во всей организационной структуре;
  - Branch — по нормализованному `full_name` внутри найденного Holding;
  - Production Department — по нормализованному `full_name` внутри найденного Branch.
- Найденные однозначные объекты повторно используются; отсутствующие создаются.
- Если в БД найдено несколько объектов, соответствующих одному критерию сопоставления в пределах области уникальности, импорт отклоняется как неоднозначный.
- Одинаковые наименования дочерних объектов в разных родительских объектах допустимы.

### 32.4. Шаблон оборудования

- Формат: `.xlsx`.
- Единственный лист с точным названием `Оборудование`.
- Первая строка — заголовки; данные начинаются со второй строки.
- Одна строка соответствует одному URZA либо одному Connection без URZA.
- Наименование Holding, Branch, Production Department, Substation и Connection повторяется в строках, чтобы каждая строка однозначно задавала путь объекта в иерархии.
- В одном файле разрешены подстанции разных ПО и филиалов, если все указанные организационные объекты уже существуют.

### 32.5. Нормализация, сопоставление и уникальность

Для сопоставления наименований и поиска дубликатов применяется единая нормализация:

- удалить пробелы в начале и конце;
- последовательности внутренних пробелов заменить одним пробелом;
- сравнивать без учёта регистра;
- при создании сохранять исходное написание после удаления пробелов по краям; внутреннее написание не переписывать только ради нормализации.

Области уникальности:

| Объект | Область |
|---|---|
| Holding | Вся организационная структура |
| Branch | В пределах Holding |
| Production Department | В пределах Branch |
| Substation | В пределах Production Department |
| Connection | В пределах Substation |
| URZA | В пределах Connection |

SAP-коды и ASUREO-коды не являются идентификаторами сопоставления; их уникальность не проверяется, совпадающие значения разрешены. Адреса также не проверяются на уникальность.

Для импорта оборудования:

- Holding, Branch и Production Department только находятся в БД; автоматически создавать отсутствующий уровень запрещено.
- Поиск выполняется последовательно: Holding → Branch внутри Holding → Production Department внутри Branch.
- Отсутствие любого уровня означает отказ всего файла; в отчёте указываются проблемное наименование и строки.
- Substation должна быть новой в рамках соответствующего Production Department. Если она уже существует, весь файл отклоняется.
- Запрещено обновлять существующие объекты, дополнять существующую Substation новыми Connection/URZA, а также импортировать отдельные Connection или URZA в уже существующую Substation.
- Новая Substation загружается целиком со всеми указанными в файле Connection и URZA. Отсутствие объекта в файле не означает его удаление или архивирование.
- В пределах одного Production Department две разные группы Substation с одинаковым нормализованным именем — ошибка. Повторные строки одной и той же Substation для перечисления её Connection/URZA допустимы.
- В пределах одной Substation дублирующиеся Connection по нормализованному имени запрещены.
- В пределах одного Connection дублирующиеся URZA по нормализованному имени запрещены.
- Повторное указание одного и того же объекта в строках допустимо только как перечисление его дочерних объектов; противоречивые значения атрибутов одного объекта между строками — ошибка.
- Одинаковые имена Connection в разных Substation и URZA в разных Connection допустимы.
- Если хотя бы одна Substation из файла конфликтует с БД или в файле обнаружено другое нарушение, отклоняется весь файл; частичное создание и автоматическое объединение запрещены.

### 32.6. Типы, значения и валидация полей

- Поля Enum в XLSX используют выпадающие списки с русскими человекочитаемыми значениями. Импортёр преобразует их в соответствующие Python enum values. Серверная проверка обязательна независимо от выпадающего списка.
- Допустимые значения Enum должны соответствовать текущим enum проекта: `HighestVoltage`, `OperationalCurrentType`, `URZAStatus`, `ElementBase`, `URZACategory`, `RoomCategory`. Не дублировать и не вводить новые варианты вне доменных Enum.
- Boolean-поля представлены выпадающим списком `Да` / `Нет`: подчинение РДУ присоединения, подчинение РДУ УРЗА и сложность УРЗА. Значения двух уровней подчинения независимы.
- `commissioning_date` — обязательная дата для указанной URZA; ячейка должна содержать тип даты Excel, отображение `ДД.ММ.ГГГГ`, не текст.
- Обязательные поля проверяются на наличие содержимого после удаления пробелов по краям.
- Пустые необязательные строки и строки, состоящие из пробелов, преобразуются в `None`.
- Ограничения максимальной длины проверяются по соответствующим ограничениям моделей/схем проекта.
- Для координат широта и долгота должны быть заполнены одновременно либо обе пусты. Географические диапазоны отдельно не проверяются.
- SAP/ASUREO и адрес не проверяются на уникальность.

### 32.7. Общие требования к XLSX

Для обоих файлов:

- Допускается только расширение `.xlsx`; проверяется также фактический формат содержимого, чтобы файл другого формата с переименованным расширением не принимался.
- В книге должен быть ровно один лист с указанным для соответствующего шаблона именем. Любые дополнительные листы, в том числе пустые, запрещены.
- Первая строка — только заголовки утверждённых столбцов. Заголовки должны совпадать с шаблоном и располагаться в фиксированном порядке. Данные начинаются со второй строки.
- Любые посторонние значения правее последнего утверждённого столбца или ниже таблицы запрещены. Полностью пустые строки внутри таблицы разрешены и игнорируются.
- Размер файла — не более 5 МБ.
- Максимум строк данных: 10 000 для оборудования и 500 для организационной структуры. Полностью пустые строки не учитываются в лимите.
- Объединённые ячейки, скрытые строки/столбцы, формулы, комментарии/примечания, гиперссылки, изображения, диаграммы, фигуры, текстовые поля, иные встроенные объекты, именованные диапазоны и защита листа/книги запрещены.

- Все прочие элементы/возможности Excel, не перечисленные как разрешённые, запрещены.

### 32.8. Проверка, ошибки и подтверждение

- Проверка файла выполняется до любых изменений в БД.
- При обнаружении ошибок система собирает все обнаруженные ошибки за один проход, если структура файла позволяет продолжить чтение. Техническая ошибка, делающая чтение невозможным, может остановить проверку с отдельной диагностикой.
- Предупреждений нет: любое нарушение — ошибка и безусловный отказ всего файла. Необязательность поля не означает допустимость некорректного заполненного значения.
- Отчёт должен указывать строку и ячейку, когда применимо, тип и описание ошибки, контекст иерархии, ожидаемое и фактическое значение, если это полезно для исправления.
- При наличии хотя бы одной ошибки подтверждение и запись запрещены. Пользователь исправляет исходный файл и загружает его заново; все проверки выполняются с нуля. Частичное исправление внутри системы не предусмотрено.
- Если ошибок нет, показывается краткая сводка создаваемых объектов: для оргструктуры — Holding/Branch/Production Department; для оборудования — Substation/Connection/URZA. Для оргструктуры можно отдельно показать количество найденных и повторно используемых существующих организаций.
- Только после отдельного подтверждения пользователя разрешается запись.
- Браузер удерживает выбранный XLSX-файл в памяти JavaScript и повторно отправляет тот же файл при подтверждении. Сервер не сохраняет загруженный файл и результаты предварительной проверки.
- При подтверждении сервер заново выполняет полную проверку файла и повторно проверяет критичные условия БД. Срок действия предварительной проверки (TTL) не используется.
- Непосредственно перед записью, внутри транзакционного сценария, повторно проверяются критичные условия и актуальность организационных ссылок/конфликтов. Если состояние БД изменилось так, что импорт больше не соответствует проверенным условиям, вся операция отменяется; пользователю требуется новая загрузка и проверка.
- Создание всех объектов конкретного импорта выполняется одной транзакцией. При любой ошибке все изменения этой операции откатываются. Репозитории не выполняют самостоятельный `commit()`; транзакцией управляет application/service слой по общим правилам проекта.

## 34. Сводка работ и решений на 08.11.2026 — паспорта, протоколы ТО и workflow ТО

### 34.1. Статус задачи «Паспорт УРЗА — протоколы ТО»

Подтверждённое поведение:

- Инженер может редактировать запись ТО в статусе `DRAFT` и отправлять её на согласование.
- Руководитель соответствующего производственного отделения может утвердить запись либо вернуть её на доработку с обязательным комментарием.
- Для самостоятельных записей ТО (`task_id is None`) используются собственные переходы статусов и очередь самостоятельных рабочих элементов.
- Самостоятельные записи ТО не дублируются в очереди заданий.

- Если связанный переход через `TaskService` завершается ошибкой, транзакция откатывается; частичное изменение статусов не должно сохраняться.

## 35. Сводка работ и решений на 08.11.2026 — структурированное логирование и email-alerts

### 35.1. Статус

реализованы, проверены целевыми тестами и отправлены пользователем в GitHub.
Дополнительное ужесточение валидации email-адресов также выполнено, проверено,

### 35.2. Базовое JSON-логирование

Commit: `941454e feat(logging): add structured JSON logging to stdout`.

- Используется стандартный `logging`, JSON formatter и stdout; файловые логи
  приложением не создаются.
- Настройка применяется при создании web app и не затрагивает CLI-сценарии
  backup/email digest.
- JSON содержит UTC timestamp, level, logger и message; исключения включают
  тип и traceback.
- `LOG_LEVEL` поддерживает DEBUG, INFO, WARNING, ERROR и CRITICAL; значение
  по умолчанию — INFO.
- Логи `uvicorn.error` направляются через общий JSON handler; `uvicorn.access`
  отключён.
- Повторная конфигурация не должна приводить к дублированию обработчиков и
  записей.
- По отчёту пользователя/Codex: целевые тесты — 22 passed; проверены запуск и
  остановка Uvicorn, HTTP 200 на `/health` и отсутствие access log.

### 35.3. HTTP request context

Commit: `f1ef68d feat(logging): add HTTP request context to structured logs`.

- `RequestContext` хранит `request_id` и необязательный `user_id` в одном
  `ContextVar`.
- ASGI middleware создаёт собственный UUID7 request ID, возвращает его в
  response header и логирует завершение запроса/необработанную ошибку.
- Query string не включается в сообщение о запросе; контекст сбрасывается в
  `finally`.
- Отмена запроса не должна ошибочно классифицироваться как HTTP 500.
- `user_id` устанавливается только после успешной аутентификации и проверок.
- Backup worker запускается в пустом `contextvars.Context()`.
- По отчёту пользователя/Codex: адресные проверки — 46 passed, 4 deselected;
  отдельный более широкий запуск ранее дал 49 passed, но повторный запуск
  DB-зависимых тестов был ограничен отсутствием доступа к локальной PostgreSQL
  в sandbox. Полный pytest не запускался.

### 35.4. Email-уведомления ERROR/CRITICAL

- Добавлен отдельный параметр `ERROR_EMAIL_TO`; пустое значение отключает
  уведомления. `FEEDBACK_EMAIL` и `BACKUP_EMAIL_TO` для них не используются.
- При включённых уведомлениях SMTP-конфигурация проверяется при старте;
  требуется ровно один из режимов STARTTLS/SSL, SMTP без шифрования запрещён.
- Уведомления отправляются только для ERROR и CRITICAL.
- Используется ограниченная очередь `queue.Queue` (100 элементов) и один
  daemon worker thread с собственным event loop. Logging handler не выполняет
  SMTP-вызовы и не блокирует event loop.
- Повторные события с одинаковым fingerprint подавляются на 300 секунд;
  fingerprint учитывает logger, level, тип исключения и нормализованное
  сообщение. Cooldown начинается после успешной постановки в очередь.
- В письмо включается только безопасный allowlist: UTC timestamp, level,
  component/logger, request_id при наличии и тип исключения. Текст исключения,
  traceback, user_id, заголовки, cookies, токены, пароли, request body и
  содержимое файлов в письмо не включаются.
- Ошибки самой подсистемы уведомлений не должны запускать рекурсивные alerts.
- При shutdown handler снимается, очередь обрабатывается с ограничением
  ожидания до 35 секунд; аварийное завершение процесса может привести к потере
  оставшихся уведомлений.
- Используется существующий `SMTPEmailSender`; его контракт и сценарии
  feedback/digest/backup не менялись.
- Поддерживается один активный handler на процесс и reference counting для
  нескольких FastAPI lifespan.
- По отчёту пользователя/Codex: целевой набор — 110 passed, 4 deselected;
  полный pytest и реальная отправка через SMTP не выполнялись.

### 35.5. Дополнительная валидация email-адресов

После независимого просмотра реализации обнаружено, что первоначальная
проверка адресов была слишком permissive. Пользователь выполнил отдельную
узкую правку `_validate_address()` в
`app/infrastructure/emailing/error_notifications.py` и добавил тесты в
`tests/infrastructure/emailing/test_error_notifications.py`.

- Local part проверяется как практический ASCII dot-atom.
- Домен проверяется как набор DNS-меток.
- Проверяются общий размер адреса, длина local part и DNS-меток, допустимые
  символы, пустые части, точки и дефисы.
- Поддерживаются распространённые ASCII-адреса, включая `+` и `_` в local
  part; Unicode-домены должны передаваться в punycode.
- Quoted local parts, комментарии, domain literals и Unicode-адреса намеренно
  не поддерживаются.
- Сообщения `ErrorEmailConfigurationError` сохраняют имя соответствующей
  настройки (`ERROR_EMAIL_TO` или `SMTP_FROM_EMAIL`); секреты не раскрываются.
- По отчёту пользователя: целевой pytest — 70 passed, 2 предупреждения
