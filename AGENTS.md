# AGENTS.md — RZAdb / База Данных РЗА

## 1. Назначение

RZAdb — внутреннее веб-приложение для учёта оборудования РЗА, подстанций, присоединений, устройств РЗА, технической документации, формуляров, уставок, схем, ТО, программ, инструкций, осмотров и задач.

Проект некоммерческий.

Этот файл — рабочие инструкции для coding agents. `DATABASE_DESIGN.md` фиксирует согласованные доменные и архитектурные решения.

Главное правило: **не добавлять новые сущности, поля, связи или бизнес-правила без отдельного доменного решения пользователя.**

## 8. Доменные правила

- Напряжения: `500, 220, 110, 35, 10, 6, 0.4`.
- SAP/ASUREO не делать глобально уникальными без отдельного доменного решения.
- Диспетчерские имена уникальны в соответствующих доменных областях.
- Имя УРЗА уникально внутри присоединения.
- УРЗА II обслуживается персоналом категорий II, III, IV.
- ОТД, Уставки, Схемы, ТО и Программы — один логический уровень под URZA.
- Инструкция URZA — отдельная версионируемая сущность под URZA.
- Инструкция РЗА — отдельная сущность уровня Substation.
- Формуляр — логическая группировка.
- Старые версии документов не удаляются.
- Для ТО подписанная форма/скан обязательна.
- Для ОТД подпись не обязательна.
- Плановая дата ТО хранится для последующего микросервиса.
- Inspection/Осмотр ПС — отдельный процесс, не обычная Task.

## 9. Versioning

Версионируемые документы не перезаписывать:

```text
current version
      ↓
new version
      ↓
old version remains in history
```

ОТД имеет текущую и исторические версии.

Инструкция URZA также имеет версии.

Переключение исторических версий в UI выполняется через HTMX без полной перезагрузки страницы.

История при первом открытии свернута; после перехода между версиями через историю она остаётся раскрытой.

## 10. Files

Бинарные файлы не хранить в PostgreSQL.

Целевой storage: S3-compatible object storage.

Не использовать универсальную полиморфную связь:

```text
File(owner_type, owner_id)
```

Использовать явные FK от доменных сущностей к `files.id`.

Целевой общий механизм:

```text
пользователь
→ AccessService
→ доменный объект
→ FileAccessService
→ File
→ ObjectStorage
→ Просмотр / Скачать
```

### Принятые решения по file access

- `AccessService` остаётся источником истины для прав на доменные объекты.
- `FileAccessService` определяет, имеет ли пользователь право читать конкретный `File` через его владельца.
- `FileOwnerResolver` определяет владельца по существующим явным FK; полиморфные `owner_type/owner_id` не вводятся.
- Один `File` должен иметь одного однозначного владельца. Несколько ролей файлов у одного владельца допустимы.
- Если у `File` несколько разных владельцев, состояние считается неоднозначным и доступ запрещается как техническая ошибка.
- Orphan-файл без владельца не доступен обычному пользователю; очистка orphan-файлов — отдельная будущая операция.
- Архивирование владельца не блокирует доступ к его файлам, если сам пользователь имеет право просматривать архивный объект.
- Архивированный сам `File` недоступен через обычные read routes.
- Для `Inspection` владелец файла определяется через `Inspection.substation_id`.
- Отдельная авторизация через `InspectionTask` для уже созданного результата осмотра не требуется.
- Просмотр и скачивание используют один общий защищённый механизм; PDF viewer не требуется.
- Не создавать отдельные несогласованные file routes для каждой сущности.

### Текущее состояние

Уже реализованы и проверены:

- `FileOwnerResolver`;
- `FileAccessService`;
- защищённые routes просмотра и скачивания;
- проверки аутентификации, владельца, архивного `File`, orphan и ambiguous ownership.

Следующая работа с файлами — **write/UI**: загрузка, привязка и действия с файлами в документных вкладках URZA.

## 11. Tasks

Типы:

```text
OTD
SETTINGS
SCHEMES
MAINTENANCE
PROGRAM
```

Статусы:

```text
CREATED
ASSIGNED
IN_PROGRESS
COMPLETED
UNDER_REVIEW
CLOSED
REJECTED
```

### Основной принцип

Task — это **рабочее поручение**, а не конкретная запись документа.

Задание относится к паре:

```text
URZA + тип работы
```

а не к существующей записи `SettingsRecord`, `SchemaRecord`, `TORecord`, `Program` и т. п.

Например:

```text
УРЗА №1
└── Уставки
    └── [Выдать задание]
```

означает:

> «Для этого устройства необходимо выполнить работу с уставками».

### Кнопка «Выдать задание»

На каждой вкладке карточки URZA, где предусмотрен соответствующий `TaskWorkType`, должна быть **одна** кнопка:

```text
[Выдать задание]
```

Кнопка относится ко всей вкладке, а не к каждой строке/записи документа.

Для текущих вкладок:

```text
ОТД           → [Выдать задание]
Уставки       → [Выдать задание]
Схемы         → [Выдать задание]
ТО            → [Выдать задание]
Программы     → [Выдать задание]
Инструкция    → [Выдать задание]
```

Кнопка не должна дублироваться у каждой существующей записи документа.

При открытии формы выдачи контекст уже известен:

```text
urza_id
work_type
```

Пользователь не выбирает заново URZA или существующую запись документа.

### Право выдачи задания

Кнопка показывается только пользователю, имеющему право выдачи задания для конкретного URZA.

Текущее доменное решение:

```text
MANAGER    → может выдавать задания в доступной области
SUPERADMIN → может выдавать задания для любого доступного ему объекта
ADMIN      → не выдаёт задания
ENGINEER   → не выдаёт задания
SPECIALIST → не выдаёт задания, если отдельным решением не определено иное
```

Проверка должна учитывать и роль, и область доступа к URZA.

UI скрывает кнопку для пользователя без права, но service/application layer обязан повторно проверять право. UI не является механизмом безопасности.

Предпочтительный business permission:

```text
can_issue_task(user, urza)
```

а не простая проверка роли в template.

### Форма «Выдать задание»

Форма открывается из контекста вкладки и не просит повторно выбрать URZA/тип работы.

Минимальный контекст:

```text
УРЗА        — только чтение
Вид работы  — только чтение
Исполнитель — выбор инженера
Срок        — ввод
Описание    — ввод
```

После подтверждения руководитель выдаёт задание конкретному инженеру.

### Workflow

Назначенное задание:

```text
CREATED
  ↓
ASSIGNED
  ↓
IN_PROGRESS
  ↓
COMPLETED
  ↓
UNDER_REVIEW
  ↓
CLOSED
```

Возврат:

```text
UNDER_REVIEW
  ↓
IN_PROGRESS
  ↓
COMPLETED
  ↓
UNDER_REVIEW
```

`REJECTED` остаётся терминальным состоянием ветки:

```text
ASSIGNED → REJECTED
```

`COMPLETED` означает, что исполнитель завершил свою работу. Это ещё не означает принятие результата.

### Права переходов

- Создание задания — руководитель/Manager в своей доступной области.
- Назначение — руководитель/Manager; Admin не назначает.
- SUPERADMIN может выполнять операции с любым доступным объектом.
- `COMPLETED → UNDER_REVIEW` выполняет назначенный исполнитель.
- `UNDER_REVIEW → CLOSED` выполняет любой активный MANAGER, имеющий доступ к URZA.
- `UNDER_REVIEW → IN_PROGRESS` выполняет любой активный MANAGER, имеющий доступ к URZA.
- Руководитель, закрывающий задание, не обязан быть тем же руководителем, который его создал или назначил.

Причина возврата на доработку обязательна.

### Результат задания

Task и документный результат — две отдельные state machine.

Не синхронизировать их автоматически без отдельного доменного решения.

Для `SCHEMES` закрытие Task требует:

```text
существует активный SchemaRecord
AND
SchemaRecord.status == APPROVED
```

Для остальных `TaskWorkType` окончательные требования к наличию и статусу результата должны быть явно определены до добавления аналогичных gate-правил.

Task-linked результат:

- Task существует и не удалён;
- `work_type` соответствует типу результата;
- URZA совпадает;
- Task назначен текущему пользователю;
- Task находится в `IN_PROGRESS`;
- для одного Task допускается один активный `SchemaRecord`/результат соответствующего типа, если это ограничение закреплено для конкретной сущности;
- soft-deleted результат не считается активным результатом.

Не считать soft-deleted результаты выполненными только потому, что физическая запись существует.

### «Выполнить задание»

В списке «Мои задания» должна быть операция:

```text
[Выполнить задание]
```

Она открывает:

```text
конкретный Task
→ конкретный URZA
→ соответствующую вкладку по work_type
```

Соответствие:

```text
OTD         → ОТД
SETTINGS    → Уставки
SCHEMES     → Схемы
MAINTENANCE → ТО
PROGRAM     → Программы
```

`task_id` должен сохраняться в контексте выполнения до создания/изменения результата.

### Прямой ввод

Прямой ввод данных из вкладки URZA и выполнение назначенного Task должны использовать один механизм согласования.

Результат прямого ввода не считается окончательно принятым после сохранения формы.

После:

```text
[Направить на согласование]
```

результат должен попасть в:

```text
UNDER_REVIEW
```

и пройти тот же review workflow.

Не создавать отдельную сущность согласования только для прямого ввода.

### Текущий фактический статус

Application/service-часть Task workflow в значительной степени реализована и покрыта тестами.

HTTP/UI ещё не завершён. В частности остаются:

- создание/выдача задания из UI;
- назначение исполнителя из UI;
- «Мои задания»;
- «Выполнить задание»;
- переход из Task к конкретному URZA и вкладке;
- сохранение `task_id` в контексте результата;
- полноценный end-to-end review через HTTP/UI;
- корректное отображение дерева/sidebar на страницах Tasks.

Известные технические проблемы по аудиту:

1. `return_for_revision()` должен вызывать проверку обязательной причины возврата.
2. Запросы результатов для OTD/Settings/Program/TO не должны считать soft-deleted результат активным.
3. Task routes должны загружать `tree`, если базовый layout/sidebar его ожидает.
4. Task list сейчас не является полноценным «Мои задания» в требуемом UX.

### Формуляры

Для операций с обязательным подписанным формуляром (в частности Уставки, Схемы, ТО) формуляр создаётся на каждую отдельную операцию, а не как общий журнал.

Источник шаблонов:

```text
data/document_templates/
├── schemes/
├── settings/
└── maintenance/
```

Сформированный документ содержит шапку конкретного объекта, одну заполненную строку текущей операции и место для подписи исполнителя.

На текущем этапе используется DOCX без серверной конвертации в PDF. PDF viewer и DOCX→PDF не вводить без отдельного доменного решения.

- **Инструкция URZA** — version/status workflow есть, но race-safe выдача `version_number` и Task integration ещё не завершены.
- **Tasks** — application/service workflow в значительной степени готов, HTTP/UI end-to-end не завершён.
- **Files** — защищённое чтение готово; upload/attach/write UI ещё не завершены.
- **Inspection** — model/service/read UI есть, полноценный HTTP/UI write workflow отсутствует.
- **Substation Instruction / Selectivity Scheme** — read/history есть, полноценный write workflow отсутствует.
- **Substation / Connection / URZA write** — полноценное редактирование объектов не завершено.
- **Production S3** — не подключён.
- **Backup / Restore, cold storage, archive UI, search, notifications** — TODO.

### Важные UI/технические замечания аудита

- В Task routes не загружается `tree`, из-за чего страницы Tasks теряют ожидаемый sidebar/tree context.
- В таблице Schemes CSS widths не соответствуют фактическим 8 колонкам.
- В таблице Maintenance у последней колонки нет корректной ширины, file action buttons визуально слишком малы.
- Для Task return обязательная причина должна реально валидироваться service.
- Soft-deleted результаты не должны удовлетворять условиям выполнения Task.
- `Connections` не являются отдельной вкладкой Substation; дерево остаётся основным способом навигации по иерархии.

Контрольный аудит считается текущим baseline. Не повторять полный аудит без изменения кода или отдельной причины.

## 19. Особые отложенные вопросы

### Исторические ТО

Текущее поле `historical_data` в модели ТО пока не перерабатывать без отдельного доменного решения.

По исходному workflow исторические ТО должны вводиться отдельным процессом.

### Уникальность dispatch_name

Перед добавлением DB-ограничений необходимо отдельно зафиксировать области уникальности `dispatch_name` для Enterprise / Substation / Connection / URZA и проверить существующие данные.

### Production S3

Подключать после стабилизации общего file contract и write/UI работы с файлами.

### Backup / cold storage

Проектировать после стабилизации storage contract.
